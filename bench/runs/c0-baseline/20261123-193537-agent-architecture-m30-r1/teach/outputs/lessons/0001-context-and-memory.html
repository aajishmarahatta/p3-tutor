Context and memory in an agent

By the end of this lesson you can decide, for any piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a manual the assistant searches.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both are memory problems, and both decide your cost per request, which your sponsor's budget limits. This lesson gives you the vocabulary and the decision rule to defend those choices at your design review.

Warm-up 2 min

Two questions from the agent loop, so today's ideas have something to stand on.

Recall

In one run of the loop, the assistant asks for check_calendar. Which part of the system actually runs that tool: the model or the program around it?

Check your answer

The program. The model only writes a request naming the tool and its arguments. The program runs the tool and puts the result back in front of the model.

Recall

Is each trip around the loop a separate call to the model, or one long call that keeps going?

Check your answer

Separate calls. That fact is the key to everything below: if every step is a fresh call, then what the model "remembers" at each step is whatever the program chooses to send it.

The context window 6 min

Start with one request. A student types: "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?"

When the program calls the model for the first time, it sends text. That text is everything the model will see on that call. It contains four things:

  1. the system prompt: your instructions ("You are the makerspace assistant. Never book without checking training."),
  2. the tool descriptions: the name and explanation of check_calendar, search_manuals and the others,
  3. the conversation so far: the student's messages and the model's earlier replies,
  4. the tool results that have come back.

Models read and write text in small pieces called tokens: a token is a short chunk of text, often a word or part of a word. The context window is the maximum number of tokens a model can take in and produce in one call, and everything listed above has to fit inside it (Claude docs: context windows).

Think of the window as the model's desk. Only what is on the desk right now can be used. Nothing in a drawer, a filing cabinet or another building helps unless someone puts it on the desk first.

Window sizes keep growing; some current models accept up to a million tokens, and longer prompts can cost more per token (Claude docs). Check the current numbers when you choose a model, because they change.
Check yourself

The student's second message, sent ten minutes after the first, says "and what about Saturday?" The model answers correctly about the laser cutter. What made that possible?

Show the answer

The program sent the earlier messages again. The model carries nothing from one call to the next on its own; its "memory" in a conversation is the history the program puts back into the window.

What is kept between steps 6 min

Inside one request, the agent makes several model calls, one per step. The usual design is simple: each step's request and result are appended to the history, and the whole history is sent again on the next call. Nothing is thrown away unless you decide to throw it away.

Worked example: tokens sent on each call

The system prompt and tool descriptions take 1,500 tokens. The question is 30 tokens. Each model request for a tool is about 40 tokens.

  1. Call 1. The model sees 1,500 + 30 = 1,530 tokens. It requests check_calendar.
  2. Call 2. The calendar answer is 200 tokens. The model now sees 1,530 + 40 + 200 = 1,770. It requests search_manuals.
  3. Call 3. The search returns three manual pages, 3,000 tokens. The model sees 1,770 + 40 + 3,000 = 4,810. It requests check_training_record.
  4. Call 4. The record is 100 tokens. The model sees 4,810 + 40 + 100 = 4,950. It writes the final answer.

Total input across the run: 1,530 + 1,770 + 4,810 + 4,950 = 13,060 tokens, though the longest single call was under 5,000. You pay for the sum, not the peak. (Providers can discount repeated text; that is outside this lesson, so budget with the plain sum first.)

Two things follow. First, cost: a large tool result is paid for again on every later call. If search_manuals had returned one page (1,000 tokens), the four calls would total 1,530 + 1,770 + 2,810 + 2,950 = 9,060, about 4,000 fewer.

Second, quality. Anthropic's engineers describe context rot: as the number of tokens in the window grows, the model's ability to recall information from it decreases, so context is a finite resource with diminishing returns. The goal they give is the smallest set of high-signal tokens that gets the outcome you want (Anthropic: effective context engineering for AI agents). The decline is a gradual slope, not a cliff.

A common mix-up

"If the window is big enough, I can put everything in it and stop worrying." It is tempting because a million-token window sounds like it fits every manual. But you pay for every token on every call, and a stuffed window makes the model's recall worse, not better. A big window raises the ceiling; it does not remove the need to choose what goes in.

Check yourself

A run makes 10 calls. Call 2 returns a 5,000-token tool result that is never needed again. About how much does that one result add to the total tokens sent over the run?

Show the answer

40,000. The result comes back after call 2, so calls 3 through 10, eight calls, each carry it. Dropping or shrinking results you no longer need is how an agent stays cheap.

What is kept between sessions 5 min

A session is one conversation from start to finish. When Riley's student closes the chat and comes back next week, the program starts a new session with an empty window: system prompt, tool descriptions, and the new question. Nothing else.

So by default, nothing is kept between sessions. The model has no memory of last week, and the window does not carry over. Whatever the assistant is to "remember" must be saved outside the model, by the program, and put back into the window when needed.

A common mix-up

"The assistant will remember the student, because it talked to them before." It is tempting because people remember conversations. But the model is the same fixed program on every call, and it learns nothing from your users. Without a saved record, the second visit is a first visit.

Check yourself

Your sponsor suggests: "Just switch to a model with a bigger window, then it will remember each student's training." What is wrong with that?

Show the answer

A new session starts empty whatever the window size. Window size limits one call; it is not storage.

Retrieval: finding the right page 6 min

The manuals are too long to put in the window on every call (you saw the cost above), and most of a manual is irrelevant to any one question. Retrieval means fetching only the few pieces of a large collection that are relevant to the question, and putting those in the window.

There are two moments to retrieve. Anthropic's context-engineering post names both (source):

  • Up front: the program searches before the model's first call and puts the best matches in the prompt. The post describes the common version, embedding-based retrieval, which finds pieces whose meaning is close to the question.
  • Just in time: the model carries only light references, like file names or stored queries, and calls a tool such as search_manuals when it needs something. This is how the loop you already know works.

Up front is simple and fast, but it guesses what is needed before the model has thought. Just in time lets the model choose, but it takes more steps, and an agent with poor tools can waste its window. The post's recommended middle ground: load a small amount of essential material up front and let the agent fetch the rest as it goes, and, in its words, "do the simplest thing that works."

Retrieval depends on the tool doing two things well: finding the right pages, and returning them in a compact form. A search that returns 3,000 tokens when 800 would do is the call-3 jump in Figure 2.

A common mix-up

"Retrieval means the model has read the whole manual." It has read only what came back. If the search missed the right page, the model cannot know, and may answer confidently from the wrong one. That is why you test the search on real student questions, not only the model.

Check yourself

A student asks how to change the blade on the vinyl cutter. The vinyl cutter manual has 12 pages. Which design is the best fit for a small budget?

Show the answer

Search and load the matching page. You pay for one page and the answer comes from your machine's manual.

Notes as memory 5 min

Retrieval brings in documents that already exist. Notes are the other direction: the agent writes something down, outside the window, and reads it back later. Anthropic calls this structured note-taking, or agentic memory: the agent regularly writes notes to memory outside the context window and pulls them back in at later times. Their examples are a to-do list and a NOTES.md file (source). In their Pokémon-playing example, the agent keeps tallies over thousands of steps and, after its context is reset, reads its notes and carries on.

For the makerspace, a note can be a short record per student:

student: s-4821
laser_cutter_training: passed 2026-10-03
prefers: afternoon slots
last_booking: laser cutter, Fri 3 pm

At the start of a session, the program loads this record into the window (about 40 tokens). When something worth keeping happens, the assistant calls a tool such as save_note. Two tools, a read and a write, give you memory between sessions.

Notes also help within a long run. When a window nears its limit, compaction summarizes the conversation and restarts with the summary. Anthropic's version keeps decisions, unresolved problems and key details, and discards redundant tool output. Their advice is to first make sure the summary misses nothing important, and only then trim it. The lightest form is simply clearing old tool results that are no longer needed (source).

What belongs in a note

  • Facts that last and that you cannot look up elsewhere: training status, stated preferences.
  • Not facts that go stale: "Friday 3 pm is free" is wrong by Saturday. Keep the calendar as the one source of truth and query it each time.
  • Small: a note is loaded every session, so it is paid for every session.
Check yourself

Which of these is the better thing for the assistant to save as a note?

Show the answer

The training result. It lasts, belongs to one student, and exists nowhere else. Availability belongs to the calendar and thickness limits to the manual.

Worked example and practice 8 min

The decision rule, in four questions to ask about any piece of information:

  1. Is it needed right now, in this step? If yes, it goes in the window, as small as it can be.
  2. Will it still be true and useful in a later session? If yes, save it as a note.
  3. Is it big, and only a small part is needed at a time? Then keep it as a searchable document and retrieve.
  4. Is it old and no longer needed in this run? Clear or summarize it.
Worked example

Sort four items for the assistant. For each, say where it lives and why.

  1. "Passed laser training on Oct 3." Question 2: it lasts and cannot be looked up elsewhere. A note, loaded at the start of each session.
  2. The 60-page laser cutter manual. Question 3: big, and any question needs two pages. Searchable document; retrieve pages on demand.
  3. The calendar answer for tomorrow, just fetched. Question 1: needed now, stale soon. Window only; never saved.
  4. The 3,000-token search result from 20 steps ago, now answered. Question 4: clear it so it stops being resent and stops crowding the window.
Your turn

Sort these four items the same way. The first is done for you: the 3D printer's troubleshooting guide: a searchable document, because it is big and a question needs one section. Now do the other three.

  • A student says, "I'm only free on Tuesday and Thursday mornings."
  • The month-long booking list returned by a tool 30 steps ago, now irrelevant.
  • The confirmation text for the booking made a moment ago.
Show a solution
  • Stated availability: a note. It is a lasting preference that only the student can tell you. (Ask first if you want to be sure they want it saved.)
  • The old month-long list: clear it. It is large, stale and no longer needed in this run.
  • The booking confirmation: window for now, so the model can confirm to the student. The booking itself already lives in the booking system, so there is no need to save a second copy as a note.

Summary 2 min

  • The model sees only what is in the context window on each call: system prompt, tool descriptions, conversation and tool results. The program re-sends it every call, and you pay for it every call.
  • Within a run, history is appended and grows; large tool results get paid for repeatedly and can hurt recall. Between sessions, nothing carries over unless the program saves it.
  • Retrieval fetches only the relevant pages of a big document. Notes save small, lasting facts outside the window. Compaction and clearing trim what the window holds.

Say it in your own words: without looking, explain to a teammate why a student's training status is a note, the laser cutter manual is retrieved, and tomorrow's calendar slot is neither.
