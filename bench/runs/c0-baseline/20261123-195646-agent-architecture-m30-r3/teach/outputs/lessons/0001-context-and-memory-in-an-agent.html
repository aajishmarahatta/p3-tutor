Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a library it searches on demand, and say why.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (objective O1)
Why this matters for you

Your assistant has to answer from long machine manuals, and remember each student's training status between visits, on a small model budget. Those are three different memory problems, and each has a different answer. This lesson gives you the vocabulary to defend those choices at your design review.

Warm-up 2 min

Two questions from the agent loop, from memory. Try them before you open the answers.

Recall

The model asks for check_calendar("laser cutter", "Friday"). Who actually runs that tool: the model, or the program around it?

Check your answer

The program runs it. The model only writes a request that names the tool and its arguments. The program runs the tool and then sends the result back to the model. That last step matters today: it is how things get into the model's context.

Recall

A student asks, "Is the laser cutter free on Friday?" and the assistant calls one tool before answering. How many times is the model called?

Check your answer

Two. The first call ends in a tool request. The second call sees the tool result and writes the final answer. Every step in the loop is a separate model call. Keep that in mind: it is the key to everything below.

The context window: what the model sees 6 min

Start with a concrete case. A student types: "How do I change the blade on the band saw?" The program calls the model. What does the model receive?

It does not receive "the student's question" alone. It receives one long piece of text made of several parts: the assistant's instructions (the system prompt), the definitions of the tools it may call, and the conversation so far, ending with the new question. All of that text is the model's input for this call.

The context window is the most text the model can look at in one call, and that includes its own reply. The Claude documentation calls it the model's "working memory" and separates it from training data: the model learned patterns during training, but only what is in the context window is in front of it right now (Claude docs: context windows).

Models read and count text in tokens: small pieces of text, often a short word or part of a word. Both the window size and the price are measured in tokens. A page of a manual is typically several hundred tokens, so a long manual can run to tens of thousands.

Three facts to hold on to

  1. The model has no memory of its own between calls. Each call starts fresh. If a fact is not in the text sent this time, the model does not have it.
  2. Everything in the window counts as input, and input costs tokens. The docs say each turn's input holds all earlier history plus the new message, and that tool results, the system prompt and the tool definitions all count (context windows).
  3. More is not automatically better. The same page describes context rot: as the number of tokens grows, accuracy and recall degrade. Anthropic's engineering team describes this as a finite "attention budget" that every new token uses up, and says the aim is "the smallest possible set of high-signal tokens" for the job (Effective context engineering for AI agents).
A common mix-up

"The assistant remembers the conversation, so memory is built in." It is tempting because chat apps feel like they remember. What actually happens is that the program re-sends the earlier messages every time. Take that re-sending away and the model knows nothing about the earlier turns. The same goes for the next day: unless your program saves something and puts it back into the context, the model starts blank.

Check yourself

A student asks the assistant a follow-up question: "And what about the other blade?" The model answers correctly. What is the best explanation?

Show the answer

The third option. The model keeps nothing between calls; the program re-sent the earlier turns, so they were in the context.

What is kept between steps 6 min

Now put the loop from the last lesson together with the context window. Take "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?" The assistant has three steps: check the calendar, search the manuals, then answer.

Within one request, what is kept between steps is simply this: the program appends each new item to the context and sends the whole thing again. The context is a growing list.

Two consequences matter for your budget and your design.

Cost. You pay for the whole context on every call, not only for the new part. A large tool result, such as a full manual page, is paid for again on each later call. Prompt caching can make the repeated part cheaper, but the docs are explicit that cached text still fills the window: caching changes what you pay, not whether it counts (context windows).

Quality. A long loop fills the window with old tool results the model no longer needs. Anthropic describes several ways to handle that (context engineering post):

TechniqueWhat it doesMakerspace use
Clear old tool resultsDrop bulky results the model has already usedDrop the full calendar dump after the free slot is found
CompactionSummarize a nearly full conversation and start a new window with the summaryA long booking chat that wanders through many machines
Sub-agentsA helper works in its own clean window and returns a short summarySearching a long manual and reporting only the answer

For a makerspace assistant, most requests are short, so you may never need compaction. The first design move is cheaper: keep tool results small.

The first option. The input grows with each step because earlier requests and results are re-sent.

What is kept between sessions: notes 7 min

Now the second problem. On Monday, Sam completes the laser cutter safety training. On Thursday, Sam opens a new chat and asks, "Can I book the laser cutter?" A new chat means a new context window, empty except for your instructions. The model cannot know about Monday.

The fix is old and simple: write it down. Notes (also called agent memory) are information saved outside the context window, by the agent or the program, and loaded back when needed. Anthropic describes structured note-taking as the agent regularly writing notes to memory outside the context window and pulling them back in later; a to-do list or a NOTES.md file are examples (context engineering post).

A worked picture of notes

For Sam, the saved note could be one line in a file or database row:

students/sam.txt
laser cutter safety training: passed 2026-11-16
band saw: not trained
prefers evening slots

On Thursday, the program looks up Sam's file when the chat starts and adds its text to the context. Now the model "remembers", because the text is in front of it. Memory is saved text plus a step that puts it back.

Two ways to wire it

  • The program does it. Your code loads the student's record at the start of a session and writes updates when a booking or training changes. The model never touches storage. This is simple and predictable.
  • The model does it, through a tool. You give the model a memory tool and it decides what to read and write. Claude's memory tool works this way: it is client-side, so "Claude requests file operations, and your application runs them" against a /memories folder that your code maps to real storage, such as a per-user directory or a database. The commands are view, create, str_replace, insert, delete and rename (Claude docs: memory tool).

The second way is the same loop you already know: the model writes a request, the program runs it. Your handler also has to reject paths outside the memory folder, so the model cannot be tricked into reading other students' files.

Training status is a record the booking rules depend on. Treat it as data your program owns, not as something the model should "remember" and possibly get wrong. A safe design lets the model read the record through a tool, while only your code changes it.
A common mix-up

"A bigger context window means the assistant can remember students." A bigger window only holds more text within one call. It does not carry anything into the next call or the next day, and it makes every call larger and costlier. Persistence needs storage outside the window.

Check yourself

Which item is best saved as a note and loaded when a student starts a chat?

The third option: short, per-student, long-lived. The manual is for retrieval; the calendar result is step-level working data.

Retrieval: finding the right page 6 min

The third problem: the machine manuals. Suppose they total 600 pages, about 300,000 tokens. Pasting them into every call would cost a fortune on each step, may not fit, and by the context-rot argument would make answers worse.

Retrieval means searching a stored library for the few pieces relevant to the question and putting only those into the context. Anthropic's term for the agent version is "just-in-time" retrieval: the agent keeps light references, such as file paths or stored queries, and loads data with tools at the moment it needs it (context engineering post).

How a typical retrieval system works

  1. Chunking, done once in advance. Split each manual into chunks: passages of a paragraph or a few. Chunks must be big enough to keep their meaning and small enough to fit the context. There is no single best size; it depends on the material (Searching for Best Practices in RAG).
  2. Indexing, done once in advance. Turn each chunk into a list of numbers called an embedding, which places texts with similar meaning close together, and store them in an index. A plain keyword index also works.
  3. Searching, done on each question. Turn the question into an embedding (or keywords) and find the top few closest chunks.
  4. Answering. Put those chunks in the context and let the model write the answer from them.

Giving the model retrieved text before it answers is called retrieval-augmented generation, or RAG. In an agent, the search is just another tool: search_manuals(machine, query) returns a few chunks, and the loop continues.

A common mix-up

"Retrieval means the model has read the whole manual." It has not: it has read the few chunks the search returned. If the search returns the wrong chunk, such as a similar-sounding section about a different machine, the model will confidently answer from it. Retrieval quality limits answer quality, so you must test the search separately from the model.

Worked example and practice 1 + 3 min

Worked example

The assistant's instructions and tool definitions take 2,000 tokens. The student's question is 50 tokens. The model asks for the calendar (a 50-token request), the calendar result is 400 tokens, then the model asks for a manual page (50 tokens), the page is 3,000 tokens, then the model writes a 150-token answer. How many input tokens does the model read across all three calls?

  1. Call 1 input is the instructions plus the question: 2,000 + 50 = 2,050.
  2. Call 2 input is call 1's input, plus the 50-token request, plus the 400-token calendar result: 2,050 + 50 + 400 = 2,500.
  3. Call 3 input is call 2's input, plus the next 50-token request, plus the 3,000-token page: 2,500 + 50 + 3,000 = 5,550.
  4. Add them: 2,050 + 2,500 + 5,550 = 10,100 input tokens. The 3,000-token page is only 3,000 tokens once, but it makes the last call large, and it would be re-sent on any call after that.
Your turn

Same request, but now the manual search tool returns the best three chunks of 300 tokens each instead of the whole page. Calls 1 and 2 are unchanged (2,050 and 2,500). Work out call 3's input and the new total. How much did retrieval save?

Show a solution

Three chunks of 300 tokens is 900 tokens. Call 3 input: 2,500 + 50 + 900 = 3,450. Total: 2,050 + 2,500 + 3,450 = 8,000 input tokens. The saving is 10,100 − 8,000 = 2,100 input tokens, and it grows with every extra call the loop makes after the retrieval. The risk is that a chunk might miss the sentence you need, so test the search too.

Apply it

Sort these into context (this call), notes (between sessions) or library (searched on demand): (a) the rule "never book a machine without a training record"; (b) "Priya prefers mornings"; (c) the 3D printer's nozzle-cleaning procedure. Give one reason for each.

Show a solution

(a) Context, in the instructions: short, needed on every request. (b) Notes: per student, small, and needed in later sessions. (c) Library: long, many other procedures sit beside it, and it is needed only for some questions.

Summary 2 min

  • The model sees only the context window in each call, and nothing carries over unless the program re-sends it. The whole context is paid for on every call.
  • Between steps, the loop appends requests and results and re-sends everything. Keep tool results small, and clear or compact when the window fills.
  • Between sessions, save short facts as notes outside the window and load them back. The model does not remember by itself.
  • For long documents, retrieve: search the library and put only the top few chunks in the context.

Say it in your own words: without looking back, explain to a teammate how the assistant "remembers" Sam's training and "knows" the band saw manual, and why neither is in the model itself.
