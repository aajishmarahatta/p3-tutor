Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a searchable manual, and you can estimate what that choice costs.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three problems come down to one question: what does the model see at each step, and what did the program save for next time? This lesson gives you the vocabulary and the arithmetic to answer that at your design review.

Warm-up 2 min

Two questions from the agent loop. Answer them in your head before you open the answers.

Recall

A student asks, "Is the laser cutter free tomorrow, and do I need training?" The model asks for a calendar check, then a training check, then answers. How many times was the model called, and who ran the two tools?

Check your answer

Three model calls: one that ends in the calendar request, one that ends in the training request, and one that writes the answer. The program around the model ran both tools; the model only asked for them. Today's key point builds on this: each of those three calls is a separate trip to the model, so something must decide what the model sees on each trip.

Recall

When the program gets a tool's result, what does it do with it?

Check your answer

It adds the result to the conversation and calls the model again, so the model can use it to decide the next step. That "adds to the conversation" is exactly what this lesson looks inside.

The context window 5 min

Start with an everyday case. You ask a friend to help plan a trip, but your friend can only read what is on one sheet of paper you hand over, and the sheet is the same size every time. Whatever is not on the sheet does not exist for them. If the sheet is full, something must come off before anything new goes on.

A language model works like that friend. Its context window is the sheet: the total amount of text the model can take in for one call. Everything the model can use for its answer has to be in it: your instructions, the tool descriptions, the conversation so far, tool results, and the reply being written. The model has no other way to know anything about your request. Anthropic's engineering team describes context engineering as deciding what goes into this limited window, and treats it as an ongoing curation job, not a one-time prompt-writing task (Anthropic, Effective context engineering for AI agents).

The window is measured in tokens, the small pieces of text a model reads and writes. A token is often a short word or part of a word; as a rough guide, a page of English is several hundred tokens. You do not need exact counts yet, only the idea that text has a size, and that the window and your bill are both measured in it.

The window limit is set by the model you choose, and it keeps changing as new models come out, so look up the current number when you pick one. The reasoning in this lesson does not depend on the number.
A common mix-up

"The model remembers our earlier chat." It is tempting, because chat apps feel like talking to a person who remembers. But the model itself keeps nothing between calls; it only sees what is in the window right now. Anything that feels like memory is the program putting text back into the window. The next section shows how.

What is kept between steps 5 min

You know that an agent calls the model once per step. If the model keeps nothing between calls, how does step 3 know what happened in step 1? The program keeps a list: the transcript (also called the message history). It holds the question, each tool request the model made and each result that came back. Before every call, the program sends the whole transcript again, plus the instructions and tool descriptions.

In Python terms it is just a list you append to, which you already know how to write:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # sends EVERYTHING
    messages.append(reply)                                # keep the model's turn
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)                 # the program runs it
    messages.append(result)                               # keep the result

This is a sketch, not a real library's code. The point is the shape: the list messages is the only "memory" between steps, and it lives in your program, not in the model.

Two things follow, and both matter for your design review. First, the program decides what the model sees, so it can also decide what to drop, shorten or summarise. Second, the history grows with every step, which brings in cost.

Why context costs money, and why too much hurts 6 min

Model usage is generally billed by the tokens it reads and writes, so a bigger window sent on every call means a bigger bill. Because the transcript is resent each step, an agent's input cost is not "the transcript once": it is the sum of the transcript at every step. Let us count with made-up but realistic numbers (they are for practice, not measurements of your system).

Worked example: the cost of one request

The assistant gets: "Is the laser cutter free tomorrow at 3 pm, and what are the settings for 3 mm plywood?" Assume the instructions, tool descriptions and question together are 1,550 tokens. Each tool request the model writes is 50 tokens. The calendar result is 300 tokens, and the manual page the search tool returns is 3,000 tokens. The model then writes the answer.

  1. Call 1 sends 1,550 tokens.
  2. The model requests the calendar (50 tokens); the result is 300. Call 2 sends 1,550 + 50 + 300 = 1,900.
  3. The model requests the manual search (50); the result is 3,000. Call 3 sends 1,900 + 50 + 3,000 = 4,950 and writes the answer.
  4. Total input over the three calls: 1,550 + 1,900 + 4,950 = 8,400 tokens.

Notice that the 3,000-token page was sent once here, because the answer came right after it. If one more step followed, that page would be sent again, and again at every later step. Big tool results are expensive twice: once to arrive, and every time afterwards.

Cost is not the only reason to keep the window lean. Anthropic's engineers note that research on long inputs has found that a model's ability to recall information from its context falls as the context grows, a problem they call context rot. Their guideline is to find the smallest set of high-signal tokens that gives you the result you want (Anthropic). So a lean window is cheaper and usually better.

What can the program do when the transcript gets long? Three common moves:

  • Keep tool results short. Return only the rows of the calendar that matter, not the whole month.
  • Clear stale results. After the model has used a big result, remove it from the transcript. Anthropic's platform offers this as context editing, which removes stale content from long-running agent sessions (Anthropic, Managing context).
  • Summarise. Replace an old stretch of the conversation with a short summary and carry on.
A common mix-up

"A bigger window means we can stop worrying about context." It is tempting, because a bigger sheet seems to remove the limit. But you still pay for every token on every call, and a crowded window can make recall worse, not better. A bigger window gives you room; it does not tell you what to put in it.

What is kept between sessions: notes 6 min

A session is one conversation from start to end. When it ends, your program's message list is gone, and the next session starts with an empty window. Everyday case: a shift worker leaves a handover note on the machine so the next person knows what happened. The note is not in anyone's head; it is on paper that the next person reads first.

For your assistant, think of the student Sam, who finished laser-cutter training on Monday and comes back on Thursday. Nothing in the model knows that. Unless your program saved "Sam: laser cutter training complete, Monday" somewhere and puts it into the window at the start of Thursday's session, the assistant will ask Sam to take the training again.

There are two ways to save things, and you can use both:

  • Your program saves facts it already knows how to save. A training record belongs in an ordinary database or file, written by your code. At the start of a session, the program looks up Sam's record and adds a line to the window. This is cheap, predictable and easy to test.
  • The model writes its own notes. For things the model discovers while working, such as a student's preferences or progress on a long task, the model can be given a notes tool. Anthropic's memory tool works this way: the model asks to view, create or edit files in a memory directory, and it is a client-side tool, which means Claude only requests the operations and your application runs them against storage you control (Claude Platform Docs, Memory tool).

Look at what that second point says: it is the same pattern you learned in the agent loop. The model asks; your program acts. "Memory" is a tool whose result happens to be a file's contents.

Saving is only half the design. Loading everything saved at the start of every session would fill the window with old text and waste money. So decide what gets loaded by default (Sam's training status: a line or two) and what is looked up only when needed.

Retrieval: finding the right page 6 min

Notes remember things the assistant learned. A manual is different: it is a large, fixed body of text that you already have. A laser-cutter manual may have hundreds of pages, and the student asks about one setting. Putting the whole manual in the window would be slow, costly and, as we saw, can make recall worse. Instead, you retrieve: search the manual first, and put only the few best-matching passages in the window.

The usual recipe, in three steps, done before any student asks:

  1. Chunk the manual into pieces, such as a section or a few paragraphs each.
  2. Index the chunks so they can be searched, by keywords, by meaning, or both.
  3. At question time, a search tool takes the student's words, returns the top few chunks, and those go into the window as a tool result.

Retrieval is therefore a tool, like the calendar check. The model calls search_manuals("laser cutter 3 mm plywood settings"), and your program returns a handful of passages. A well-chosen 500-token chunk replaces a 3,000-token page.

Worked example: retrieval changes the bill

Take the request from the cost example, but let the search tool return one 500-token chunk, not a 3,000-token page.

  1. Call 1 sends 1,550. Call 2 sends 1,900, as before.
  2. Call 3 sends 1,900 + 50 + 500 = 2,450.
  3. Total input: 1,550 + 1,900 + 2,450 = 5,900, against 8,400 before. That is about 30% less, from one design choice, and the saving grows with every extra step.

Retrieval fails in a specific way. A chunk cut out of a manual often loses the information that says what it is about. Anthropic's example of this is a chunk that does not name the company or the time period it refers to, which makes it hard to find or use. Their fix, contextual retrieval, has a model write a short explanation of each chunk in light of the whole document and attach it to the chunk before indexing. In their tests this lowered the rate of failing to retrieve the right chunk in the top 20 from 5.7% to 2.9% when combined with keyword search (Anthropic, Contextual retrieval; the figures are from Anthropic's own evaluation, on their datasets).

For your manuals the same problem looks like this: a chunk that says "Set power to 80% and speed to 15" does not say which machine or material. If it is indexed alone, a search for the laser cutter may miss it, or return it for the wrong machine. Adding "Laser cutter manual, section on cutting 3 mm acrylic" to the front of each chunk fixes that.

A common mix-up

"Retrieval and memory are the same thing." They overlap, because both put text in the window on demand, but they hold different things. Retrieval searches a large collection that exists before the conversation, such as manuals. Notes hold what the assistant or your program learned during use, such as a student's training status. Mixing them leads to bad designs, like saving whole manuals in per-student notes.

Worked example: sorting information into three places

Sort these three items for the makerspace assistant: (a) the student's current question; (b) "Priya completed bandsaw training on 3 March"; (c) the bandsaw blade-change procedure.

  1. Ask of each: does it exist before the conversation, is it a fact about this student, or is it part of this request?
  2. (a) is part of this request. It goes in the transcript and is resent each step.
  3. (b) is a short fact about a person that must outlive the session. Save it in a database or notes file; load one line at the start of the next session.

Summary 2 min

  • The model sees only its context window on each call; it keeps nothing between calls.
  • Between steps, your program's transcript is the memory, and it is resent in full each time, so cost grows with every step.
  • Between sessions, nothing survives unless your program saves it and loads it back: a database for known facts, or a notes tool the model can use.
  • For long manuals, chunk, index and retrieve a few passages instead of loading everything; label chunks with what they are about.

Say it in your own words: without looking, explain to a teammate how the assistant knows on Thursday that Sam finished training on Monday, and why you would not paste the whole laser-cutter manual into every request.
