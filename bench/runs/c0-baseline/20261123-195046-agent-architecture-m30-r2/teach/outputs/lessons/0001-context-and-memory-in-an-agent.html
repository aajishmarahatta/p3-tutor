Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a searchable manual store, and say why.

Objective O3: the context window, what is kept between steps and between sessions, retrieval and notes as memory About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three come down to one question: what does the model see on each call, and what do you put there? That is what you will practise here, and it is the part of the design you will have to defend at your review.

Warm-up 2 min

Recall

From the agent loop: a student asks, "Is the laser cutter free tomorrow?" The model asks for a calendar check. Who actually runs the check, and where does its result go next? Answer in your head or on paper first.

Check your answer

The program around the model runs the tool, not the model. The result is added to what the program sends the model on its next call, and the model then decides the next step or writes the answer. That last part is today's subject: "what the program sends the model" is the context, and everything in this lesson is about managing it.

The context window 5 min

Start with a concrete case. A student types: "Can I use the laser cutter for 3 mm acrylic, and is it free Friday?" Before your program calls the model, it assembles a pile of text:

  • the system prompt: your rules for the assistant ("You help students at the university makerspace...");
  • the tool descriptions: the name, purpose and parameters of check_calendar, search_manuals and the rest;
  • the conversation so far: the student's message, and later the model's requests and the tool results.

All of that text goes into one model call. The text the model reads for that call is its context: in Anthropic's words, "the set of tokens included when sampling from a large-language model" (Anthropic, Effective context engineering for AI agents). A token is the small chunk of text, often a short word or part of one, that a model reads and writes; a page of manual is roughly a few hundred to a thousand tokens. The context window is the maximum number of tokens the model can take in and produce in one call.

Anthropic's documentation is explicit that everything counts toward that limit: "the system prompt, every message in messages (including tool results, images, and documents), and your tool definitions" (Claude docs, Context windows). Nothing in the call is free.

Two consequences matter for your sponsor's budget. First, you pay for the tokens you send in, and they are sent on every call, so a bloated system prompt is a cost you pay each step. Second, the window is a limit, not a goal: a bigger window means more room, but not better answers. Anthropic describes context as "a finite resource with diminishing marginal returns", because as the number of tokens grows, "the model's ability to accurately recall information from that context decreases" (same article). The target is "the smallest set of high-signal tokens" that gets the job done.

A common mix-up

"With a window big enough for a whole manual, I can paste every manual into every call and stop worrying." It is tempting because the pages do fit. But you would pay for those tokens on every single call, and the model would have more irrelevant text to wade through when it looks for the one line about acrylic. A big window removes the hard limit; it does not remove the cost or the clutter.

Check yourself

Your system prompt and tool descriptions together are 2,000 tokens. A request takes five model calls. Roughly how many of those tokens do you send in total, just for the prompt and tools?

Show the answer

About 10,000: 2,000 per call times five calls. The model does not hold on to the prompt between calls; the program resends it every time.

What is kept between steps 6 min

Now follow one request through the loop. Each pass of the loop is a separate model call, and the program decides what that call contains. In the usual design the program keeps a growing list of messages and sends the whole list each time. Anthropic's documentation describes the input of each turn as "all previous conversation history plus the current user message" (Claude docs, Context windows). The model is not remembering the earlier steps; it is re-reading them.

Worked example: one request, four calls

The student asks: "Is the laser cutter free Friday at 3 pm, and what settings for 3 mm acrylic?" The token counts below are invented to show the shape, not measured.

  1. Call 1. Context: system prompt and tools (2,000) + question (40) = 2,040 tokens. The model requests check_calendar.
  2. Call 2. The program ran the tool. Context: the 2,040 + the request (30) + the calendar result (300) = 2,370 tokens. The model requests search_manuals.
  3. Call 3. Context: the 2,370 + the second request (30) + three manual passages (3,000) = 5,400 tokens. The model writes the final answer.

Total tokens read across the three calls: 2,040 + 2,370 + 5,400 = 9,810, even though no single call had more than 5,400. The earlier material is paid for again each time. Long loops with big tool results get expensive quickly, which matters for a small budget.

When the loop runs long, the context fills with old tool results the model no longer needs. There are two standard remedies, both from Anthropic's engineering guidance (Effective context engineering):

  • Clearing old tool results: once the model has used a manual passage, remove it from the list the program resends. This is the lightest form of tidying.
  • Compaction: "taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary." You trade detail for room.

Either way, the program, not the model, is in charge of the list. Deciding what to keep, what to shorten and what to drop is a design choice, and it is yours.

Check yourself

In the worked example the 3,000 tokens of manual passages arrive at call 3. Suppose the student then asks a follow-up in the same conversation, and the program keeps the passages. What happens to the cost of the follow-up call?

Show the answer

The last one. What the program keeps, it resends, and what it resends, you pay for. Clearing the passages after use would shrink the follow-up call.

What is kept between sessions 4 min

A session is one conversation: the run of messages from the first question until the program stops. Here is the situation your notes already point at. On Monday a student completes laser cutter training with a technician and tells the assistant. On Wednesday the student opens a new chat and asks, "Can I book the laser cutter?" What does the model know?

Nothing about Monday. The model's weights do not change when it talks to you, and a new session starts with a new, empty list of messages: just the system prompt, the tool descriptions and the new question. Whatever you want the assistant to know on Wednesday, your program has to write down on Monday and put back into the context on Wednesday.

A common mix-up

"The assistant remembers my earlier chats, the way a person would." Chat products can feel that way because they have a memory feature built around the model, so it is tempting to assume the model does it itself. It does not. When you call a model from code, nothing carries over between sessions unless your program saves it and sends it back. If you build nothing, the assistant forgets every student on every visit.

Notes as memory 5 min

The simplest between-session memory is the one people use: write notes. Anthropic calls this structured note-taking or agentic memory: "the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times", for example a to-do list or a NOTES.md file (Effective context engineering). The same pattern is how this tutoring workspace works: your NOTES.md is read at the start of every session.

For the makerspace assistant, a notes file for one student might be:

student: Sam Ortiz (id 4417)
trained: laser cutter (2026-11-17), 3D printer (2026-10-02)
not trained: CNC router
preferences: usually books evenings

At the start of a session the program loads this file into the context, a few dozen tokens, so the model can answer "Can I book the laser cutter?" without asking again. When the student reports new training, the model asks for a "save" tool call and the program updates the file.

Anthropic ships this as a ready-made memory tool. It is client-side: "Claude requests file operations, and your application runs them", against storage you control, under a /memories path with commands such as view, create and str_replace. This is the agent loop again: a memory write is just a tool call. The docs also warn that you must validate every path, because a request like /memories/../../secrets.env could reach files outside the memory directory.

What belongs in notes, and what does not

  • Save facts that are small, stable and needed in later sessions: training status, booking preferences, what is half-finished.
  • Do not save what you can look up fresh and that changes: the calendar, which would be stale by Friday. Call the tool again.
  • Do not save whole manuals. They are large and shared by every student, so they need a different mechanism, in the next section.
  • Think about privacy. Notes about a named student are personal data. Decide who may read them, and let students see or delete theirs.
Check yourself

Which item is the best candidate for a saved note rather than a fresh tool call?

Show the answer

The training date. Small, stable, personal and needed again: save it. The calendar should be looked up fresh, and the manual belongs in a searchable store.

Retrieval: finding the right page 6 min

The manuals are different: they are long, shared and mostly irrelevant to any one question. A student asking about acrylic settings needs one or two passages, not four hundred pages. Retrieval means searching a store of documents for the few pieces relevant to a question and putting only those into the context. When the search is done by code before the model writes its answer, the pattern is often called retrieval-augmented generation (RAG).

How a chunk search works

As described in Anthropic's write-up on retrieval, the usual recipe is: split the documents into chunks, "usually no more than a few hundred tokens"; turn each chunk into an embedding, a list of numbers that places texts with similar meaning close together; store them; and at question time find the chunks closest to the question and add them to the prompt (Anthropic, Contextual Retrieval).

Embeddings match by meaning, so a question about "cutting clear plastic" can find a passage that says "acrylic". They can miss exact strings, though. The same article notes that a search for "Error code TS-999" may be missed by an embedding search but found by BM25, "a ranking function that uses lexical matching to find precise word or phrase matches". Machine manuals are full of part numbers and error codes, so combining both searches is a sensible default.

One failure is worth knowing, because it affects how you cut your manuals. A chunk that says "Set the power to 40% and speed to 12" is useless if the model cannot tell which machine or material it describes. Anthropic's fix, contextual retrieval, prepends a short chunk-specific explanation (usually 50 to 100 tokens) before indexing. In their tests, adding contextual embeddings and contextual BM25 cut the top-20 retrieval failure rate from 5.7% to 2.9%, a 49% reduction (Anthropic, Contextual Retrieval). Those figures come from their own test sets, so treat them as a sign of direction, not a promise for your manuals. A simpler step you can take yourself: cut the manuals at section boundaries and put the machine name and section title at the top of every chunk.

Two ways to wire retrieval in

  • Search first, then ask. The program searches on the student's question and puts the top chunks into the first call. Fixed and predictable, but it runs even when the question did not need the manuals.
  • Search as a tool. search_manuals is one of the tools, and the model decides when to call it and with what query. Anthropic calls the general idea just-in-time retrieval: the agent keeps "lightweight identifiers" such as file paths or stored queries and loads data into context at runtime using tools (Effective context engineering). This is what your assistant's loop already does.
A caveat worth taking to your team: for a knowledge base smaller than about 200,000 tokens, the Contextual Retrieval article says you can "just include the entire knowledge base in the prompt". A few short manuals might qualify. Measure your corpus before you build a retrieval system, and remember the per-call cost from section one.
A common mix-up

"Retrieval means the model goes and reads the manual." The model reads only what is in its context. Retrieval is code (a search) that decides which chunks go in. If the search returns the wrong chunk, the model never sees the right one and cannot answer from it, however capable it is. When answers are wrong, look at what was retrieved before blaming the model.

Check yourself

A student asks about error "E-4471" on the vinyl cutter. An embedding search returns general troubleshooting chunks but not the one that lists E-4471. What is the most direct fix?

Show the answer

Add keyword search. Exact codes are a known weak spot of embeddings alone and a strength of BM25; the other two options do not change what the search returns.

Worked example and practice 5 min

Worked example: where does each fact go?

A student, Sam, opens a new chat and asks, "I finished 3D printer training last month. Is printer 2 free Saturday morning, and what bed temperature for PETG?" Place each fact.

  1. "Sam is trained on the 3D printer." Small, stable, personal, needed later: a saved note. Load Sam's notes into the context at the start of the session, so the assistant need not ask.
  2. "Printer 2 on Saturday morning." Changes by the hour: a tool call to the calendar, result kept only as long as it is useful.
  3. "Bed temperature for PETG." Lives in a long shared manual: retrieval. Search the manuals, put the top one or two chunks in the context.
  4. "The assistant's rules and the tool descriptions." Needed on every call: in the context always, so keep them short.
  5. After answering, clear the manual chunks from the list if the conversation continues, and do not copy them into notes.
Your turn

A different student, Priya, says: "Book the CNC router Thursday afternoon. Last time you said I still needed the safety walkthrough; I did it yesterday. What spindle speed for aluminium?" Place each of these four facts as note, tool call, retrieval or always-in-context: (a) Priya's safety walkthrough status; (b) whether the CNC router is free Thursday; (c) the spindle speed for aluminium; (d) the rule "never book a machine for an untrained student". Start with (a), which you can place the same way as Sam's training status, and do the other three yourself. One of them needs a note update as well.

Show a solution
  1. (a) A saved note, and today it also needs an update: she completed the walkthrough yesterday, so the assistant should save that.
  2. (b) A tool call to the calendar, fresh each time.
  3. (c) Retrieval from the CNC manual: search for aluminium spindle speed, put the best chunk in the context.
  4. (d) A rule in the system prompt, always in the context. Since a rule that matters this much should not depend on the model's memory of anything, the booking tool should also check the training status itself in code.

Summary 2 min

  • The context is the text the model reads on one call: system prompt, tool descriptions, messages and tool results. It is limited, it is paid for on every call, and more of it is not always better.
  • Between steps, the program keeps a list and resends it. Clear old tool results or compact the history when it grows.
  • Between sessions, nothing is kept unless your program saves it. Notes in a file or database, loaded at the start, are the simplest memory.
  • Long shared documents go in a searchable store. Retrieval is code that picks chunks for the context; combine meaning search with keyword search.
