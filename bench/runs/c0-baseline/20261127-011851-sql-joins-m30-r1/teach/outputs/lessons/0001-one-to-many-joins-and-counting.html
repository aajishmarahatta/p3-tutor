One-to-many joins: why rows multiply and how to count them

By the end of this lesson you can look at a join between students and enrollments, predict exactly how many rows it returns, and pick the count that answers "how many students?" or "how many enrollments?" correctly.

Objective O2: one-to-many joins, row counts, counting without duplication About 30 minutes Builds on your first session: INNER JOIN and LEFT JOIN
Why this matters for you

You told me you sometimes expect one row per student after a join, and sometimes mix up the number of students with the number of enrollment rows. This lesson targets exactly that. It is also the most common way analysts get wrong numbers from real data, which matters for your Data Science goal.

Warm-up 3 min

Before new material, recall from your first session. Answer in your head or on paper first, then check.

Recall

A students table has 5 students. Only 3 of them have an enrollment, and each of those 3 has exactly one. What does an INNER JOIN return, and what does a LEFT JOIN from students return?

Check your answer

INNER JOIN returns 3 rows: only students with a match. LEFT JOIN returns 5 rows: all students, with NULL in the enrollment columns for the 2 who have none. Today the twist is that students can have several enrollments, which changes these counts.

Recall

What is a foreign key, in one sentence?

Check your answer

A column in one table that holds the primary key of a row in another table, such as student_id in enrollments pointing to a row in students.

Ana has 3 enrollments, Ben has 2, Chloe has 1, and Dev has none.

A one-to-many relationship means one row in the first table can match many rows in the second, while each row in the second matches at most one in the first. Here, one student has many enrollments, but each enrollment belongs to one student. The "one" side is students, the "many" side is enrollments, and the foreign key enrollments.student_id is what links them. The relationship is described in the same terms in database design guides such as the Metabase guide to duplicated data, which names one-to-many joins as a main cause of unexpected duplicate rows.

Notice a second fact: the two tables have different grain. The grain of a table is what one row stands for. In students one row is one student. In enrollments one row is one enrollment. Many wrong counts come from forgetting that the grain of a joined result is not the grain of the table you were thinking about.

Check yourself

Which statement about these tables is true?

Show the answer

The third statement. Ana's student_id (1) appears on three enrollment rows. That repeat is the "many" in one-to-many.

Why a join multiplies rows 6 min

Start with the query, and predict before you read on.

SELECT s.student_id, s.name, e.course
FROM students s
INNER JOIN enrollments e
  ON e.student_id = s.student_id;

How many rows? Many learners say 3, one per student who has enrollments. Let us find out how a join really works. A join builds its result by pairing rows: for each row in the left table, it finds every row in the right table where the ON condition is true, and it outputs one result row per matching pair. Ana matches three enrollment rows, so she produces three result rows.

Result of the INNER JOIN (6 rows)

2BenMath

Six rows. Ana's name is repeated because her student row was paired with each of her enrollment rows. Dev has no match, so an INNER JOIN drops him.

A common mix-up

"A join keeps one row per student." This feels natural because you start from the students table and the join looks like it just adds columns. But a join adds rows too whenever a student matches more than once. The first table's rows are repeated, one copy per match. If you expected 3 or 4 rows above, count the matches instead: 3 + 2 + 1 = 6.

Check yourself

Predict first. Suppose a new student, Eli, enrolls in Math, Art, Physics and Music, so he has 4 enrollment rows. Starting from the original tables plus Eli, how many rows does the INNER JOIN above return now?

Show the answer

10. The result has one row per matching pair: 3 + 2 + 1 + 4 = 10.

A rule for predicting the row count 5 min

You can predict the size of a join without running it. Use this procedure.

  1. Find the many side (here, enrollments).
  2. For an INNER JOIN: count the many-side rows whose foreign key matches a row on the one side. If every enrollment points at a real student, that is simply the number of enrollment rows: 6.
  3. For a LEFT JOIN from the one side: start with the INNER JOIN count, then add one row for each one-side row that has no match at all. Those rows stay, with NULL in the many-side columns.

For our tables, the LEFT JOIN is 6 + 1 = 7, because Dev has no enrollments and adds one row with NULL for course.

Check yourself

Using the original tables, you run a LEFT JOIN from enrollments to students (enrollments on the left). How many rows come back?

Show the answer

6. Each enrollment matches exactly one student, so no row is repeated, and Dev is not kept because he is on the right side. Rows multiply when the left row matches many right rows, not the other way round.

Counting: three kinds of COUNT 7 min

Now the part that trips up many analysts. Take the LEFT JOIN above, with its 7 rows, and ask: how many students are there, and how many enrollments? Each question needs a different count. Remember that COUNT works on the rows of the result, after the join has happened.

COUNT(*)
Counts rows, no matter what they contain.
COUNT(column)
Counts the rows where that column is not NULL.
COUNT(DISTINCT column)
Counts the different non-NULL values in that column, so repeats count once.

These definitions are standard SQL behavior; you can confirm them in the aggregate-functions chapter of your database's manual.

Apply them to the 7-row LEFT JOIN result:

ExpressionResultWhat it counted
COUNT(*)7Every result row, including Dev's NULL row
COUNT(e.enrollment_id)6Rows with a real enrollment; Dev's NULL is skipped
COUNT(s.student_id)7Not NULL on every row, so repeats are counted
COUNT(DISTINCT s.student_id)4The four different students
COUNT(DISTINCT e.student_id)3Students who have at least one enrollment

The key habit: name the thing you are counting, then pick the expression that counts exactly that thing.

  • "How many enrollments?" Count a column from the many side that is never NULL for a real enrollment, such as COUNT(e.enrollment_id). Using a primary key is safest.
  • "How many students?" Count the distinct one-side key: COUNT(DISTINCT s.student_id).
  • "How many rows does this join return?" Use COUNT(*), and expect it to match the prediction rule from the last section.
A common mix-up

"COUNT(*) tells me how many students." It tells you how many rows, and after a one-to-many join, rows are enrollments, not students. In the INNER JOIN, COUNT(*) is 6, yet only 3 students appear. Running COUNT(*) on a join and reporting it as a number of students is the classic error: Ana is counted three times.

Check yourself

On the INNER JOIN between students and enrollments (6 rows), which expression returns the number of students who are enrolled in at least one course?

Show the answer

COUNT(DISTINCT s.student_id), which returns 3. The other two both return 6, because repeats are not removed.

Check yourself

On the 7-row LEFT JOIN result, what does COUNT(e.course) return?

Show the answer

6. Dev's row has a NULL course, and COUNT(column) ignores NULLs.

Sums and other traps 2 min

The same repetition that inflates COUNT(*) also inflates sums of one-side columns. Suppose each student pays a tuition of 1000, stored in students.tuition. After the INNER JOIN, Ana's 1000 appears on three rows, so SUM(s.tuition) gives 3000 + 2000 + 1000 = 6000, but the true total for the three enrolled students is 3000. Rule: a value from the "one" side is repeated once per matching "many" row, so aggregate it only after reducing the many side.

Two clean ways to do that:

  • Count or sum distinct keys when the quantity is a simple key, as in COUNT(DISTINCT s.student_id). Be careful with SUM(DISTINCT s.tuition): it would collapse students who happen to pay the same amount, and it silently gives a wrong answer.
  • Pre-aggregate the many side in a subquery or CTE so it has one row per student, then join. Both the Metabase guide and the LearnSQL article on duplicates in joins describe this approach.
SELECT s.student_id, s.name,
       COALESCE(c.n_enrollments, 0) AS n_enrollments
FROM students s
LEFT JOIN (
  SELECT student_id, COUNT(*) AS n_enrollments
  FROM enrollments
  GROUP BY student_id
) c ON c.student_id = s.student_id;

The subquery c has one row per student who has enrollments. Joined to students, the result has exactly 4 rows, one per student, and Dev gets 0 because COALESCE replaces his NULL with 0.

A cheap sanity check before you trust any number: compare COUNT(*) of the joined result with the row count of the table you meant to keep. If the join result is larger, a one-to-many relationship has multiplied your rows.

Worked example and practice 6 min

Worked example

A book club has a members table (Mia, Noor, Omar) and a loans table. Mia borrowed 2 books, Noor borrowed 1, and Omar borrowed none. Question: using a LEFT JOIN from members to loans, what are the row count, the number of loans and the number of members?

  1. Name the many side. Loans are the many side: a member can have several loans.
  2. Count the matches. Mia has 2, Noor has 1, so there are 3 matching pairs.
  3. Add unmatched one-side rows for a LEFT JOIN. Omar has no loans, so add 1 row. Total rows: 3 + 1 = 4. This is COUNT(*).
  4. Number of loans: COUNT(l.loan_id) skips Omar's NULL, giving 3.
  5. Number of members: COUNT(DISTINCT m.member_id) removes Mia's repeat, giving 3. (Here the number of loans and the number of members happen to match; they are still different questions with different expressions.)
Your turn

A pet clinic has an owners table (4 owners) and a pets table. Owner A has 3 pets, owner B has 1 pet, owners C and D have none. Using a LEFT JOIN from owners to pets, find: (1) the number of result rows; (2) the number of pets; (3) the number of owners with at least one pet. Step 1 is given: the many side is pets. Do the rest yourself and write each answer with the expression you would use.

Show a solution

Matches: 3 + 1 = 4. Unmatched owners C and D add 2 rows. (1) Rows = 6, from COUNT(*). (2) Pets = 4, from COUNT(p.pet_id), since C and D contribute NULLs that are skipped. (3) Owners with a pet = 2, from COUNT(DISTINCT p.owner_id), which skips the NULLs and counts A and B once each. Counting all owners would be COUNT(DISTINCT o.owner_id), which gives 4.

Summary 3 min

  • A join returns one row per matching pair. When one row matches many, the one-side row is repeated, so the result is not one row per student.
  • Predict the size: INNER JOIN = number of matches; LEFT JOIN = matches plus one row per unmatched left row.
  • COUNT(*) counts rows, COUNT(column) counts non-NULL values, and COUNT(DISTINCT column) counts different values. Name what you are counting, then choose.
  • One-side values (such as tuition) repeat once per match, so they inflate sums; reduce the many side first, or count distinct keys.
