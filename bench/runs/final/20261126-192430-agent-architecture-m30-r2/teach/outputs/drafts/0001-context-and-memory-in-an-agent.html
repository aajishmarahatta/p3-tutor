Lesson 0001 · 30 minutes

Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it is always in context, retrieved on demand, saved between sessions, or dropped, and give a reason.

Objective O3: context and memory in an agent About 30 minutes
Why this matters for you

Your assistant has to answer from long machine manuals and know each student's training status when they come back. Both are context decisions, and every token you keep in context costs part of a small model budget. This lesson gives you the vocabulary and the rules to make those calls and defend them at your design review.

Warm-up 2 min

Quick recall from the agent loop, before we build on it. A student types: "Is the laser cutter free on Friday?" The assistant is an agent with a calendar tool.

Recall 1

What does the model produce first, and what comes back after that?

Check your answer

The model does not answer yet. It writes a request to use a tool, something like check_calendar(machine="laser cutter", day="Friday"). The program runs the tool and the result (say, a list of free slots) comes back as new text for the model. Then the model writes the answer to the student, or asks for another tool.

Recall 2

Who actually runs the tool: the model or the program around it?

Check your answer

The program. The model only writes text, including the text that asks for a tool. The program reads that request, does the work, and passes the result back. Keep this in mind: it explains why you decide what the model gets to see. That is today's topic.

1. Tokens and the context window 3 min

The gist

The model only uses the text placed in front of it on each call. That text has a size limit. Everything you want the model to act on has to fit.

  • Token: a small piece of text, the unit a model reads and writes. A token can be a whole word, part of a word, or punctuation. It is not the same as a word.
  • Context: all the tokens the model sees when it produces a reply. Anthropic describes it as the set of tokens included when the model generates a reply (Effective context engineering).
  • Context window: the limit on how much context fits in one call. Think of it as the model's working space. The limit covers everything sent in and also the reply the model writes (Context windows).
  • System prompt: instructions the developer (you) writes once, such as "you are the makerspace assistant; never book a machine without checking the calendar".
  • Tool definition: the description of a tool (its name, what it does, what inputs it takes) that you give the model so it knows what it may ask for. It is text, so it sits in the context too.

Example (analogy). Picture a soccer coach at halftime with a whiteboard. Only what is written on it gets used in the talk, and the board has limited space. Whatever the coach remembers from the first half but never wrote down does not help the players, and a board crammed with every stat crowds out the one that matters. The analogy stops at one point: a coach can walk away and come back to the same board, but the model gets a fresh board on every call, as the next section shows.

Sort it

For each item, is it inside the context window on a call, or outside it? (1) the system prompt, (2) the tool definitions, (3) the student's message, (4) a tool result the program just passed back, (5) the model's own earlier reply, once the program sends the conversation back, (6) the training data the model learned from.

Show the answers
  • Items 1 to 5 are in. They are all text the program places in front of the model, and the model can use only what is placed there. Item 5 is easy to miss: the model's own words count as context too once they are sent back.
  • Item 6 is out. Training shaped the model before your assistant existed (the patterns it learned, as you explained earlier), but the training documents are not in the window. If you want the model to use a document, it has to be in the context.
  • If you put 4 or 5 outside, review the definition of context above: it is everything the model sees on one call, whoever wrote it.
Check yourself

The assistant's prompt says "laser cutter". How many tokens is that?

Show the answer

It depends on how the model splits the text. Tokens are pieces, not words, so you cannot count them by counting words.

2. Between steps, nothing is remembered 4 min

The gist

A model call has no memory of earlier calls. To make a conversation, the program re-sends the whole history every time. So the context grows with each step, and the cost (and usually the wait) grows with it.

  • Call: one request from your program to the model, which returns one reply. Each pass of the agent loop is one call.
  • Session: one run of the assistant from the student's first message to the end of that conversation.
  • Input tokens are the tokens you send in (the whole context); output tokens are the tokens the model writes back. Model usage is generally billed by tokens, so more tokens sent usually means more spend. Details such as prompt caching (cheaper repeats of an unchanged start of the prompt) can change the rate, so check your provider's pricing page; this lesson gives no prices. Both input and output tokens count toward the window (Context windows).
  • Latency: the wait before the answer arrives. Longer inputs often take longer to process; this is a rule of thumb, so measure it in your own system.
  • The Context windows docs describe this directly: each turn's input is all the prior conversation plus the new message (Context windows).

Example. A student writes: "Book the laser cutter Friday at 2pm." The loop takes three calls. Here is the program, in Python, with the model call replaced by a comment so you can see the shape:

messages = [{"role": "user", "content": "Book the laser cutter Friday 2pm"}]

# CALL 1: send messages. Model replies: tool request check_calendar(...)
messages.append({"role": "assistant", "content": "tool request: check_calendar"})
messages.append({"role": "user", "content": "tool result: Friday 2pm is free"})

# CALL 2: send ALL of messages again. Model replies: tool request book_slot(...)
messages.append({"role": "assistant", "content": "tool request: book_slot"})
messages.append({"role": "user", "content": "tool result: booked, id 8841"})

# CALL 3: send ALL of messages again. Model replies: the final answer.
  • messages is the only thing that carries the conversation. It lives in your program, not in the model.
  • Each append adds the model's last reply or a tool result. The simplified roles here are for illustration; real APIs have their own formats for tool results.
  • Each "CALL" comment sends the entire list. Nothing is "continued"; the model reads everything from the top, every time.
Worked example: counting what is re-sent

Use made-up round numbers to see the shape (real counts come from a token counter; we also ignore the model's own replies here). Say the system prompt plus tool definitions are 500 tokens, the student's question is 20, and each tool request plus result is 100.

  1. Call 1 sends 500 + 20 = 520 input tokens. The system prompt and tool definitions go along on every call, since they are part of the context.
  2. Call 2 sends those 520 plus the first tool round of 100 = 620.
  3. Call 3 sends 620 plus the second round of 100 = 720.
  4. Total input across the three calls: 520 + 620 + 720 = 1,860 tokens, though the student only typed 20. The question is not the expensive part; the repeated 500-token header and the growing history are.

Two consequences for your budget: keep the system prompt and tool descriptions short, because you pay for them on every call; and keep the number of steps per request low.

Predict

In the booking example, what does the model see on call 3?

Trace

Which calls contain the calendar result ("Friday 2pm is free")?

Show the answer

Calls 2 and 3. Call 1 happens before the tool has run, so there is no result yet. Once the result is in messages, every later call carries it.

Explain

Suppose a different request takes five calls. Why does call 5 cost more than call 1, even if the student's question is short?

Show the answer

Call 5 re-sends the question plus four rounds of tool requests and results, so its input is much larger. Cost generally follows tokens, so the same question usually costs more at step 5 than at step 1. It also arrives later. Long agent runs get expensive because of the re-sending, not because the question was long. Later we will manage this.

3. Long sessions and context rot 3 min

The gist

A bigger context is not a better context. As it fills, the model gets worse at using it. The goal is the smallest set of useful tokens, and you have tools for trimming a history that keeps growing.

  • Context rot: Anthropic's term for the effect that "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases", where recall means picking the right fact back out of the text it was given (Effective context engineering).
  • Attention budget: the article's way of saying the model has limited focus, and every extra token draws on it. So context is a finite resource, even before the window is full.
  • The target, in the article's words, is the smallest set of high-signal tokens that makes the result you want likely. High-signal means it actually helps with this question.
  • Clearing tool results: deleting old tool results from deep in the history once the model has used them. The article calls it one of the safest, lightest ways to trim.
  • Compaction: when a conversation nears the limit, summarize it and start a fresh context with the summary, keeping the important details and dropping the rest.

Example (data science). Think of a feature set for a model. One useful column among a hundred irrelevant ones is harder to use than the same column among five. Extra columns are not neutral; they drown the signal. Context works the same way: the full 40-line calendar dump, still in the history after the booking is done, is an irrelevant column. The analogy has a limit: you pick features before training, but you trim context while the session runs.

A common mix-up

"If the window is huge, trimming is pointless." It is tempting because a big window never throws an error. But the limit is only the ceiling: recall can drop long before you hit it, and you pay for every token on every call.

When trimming goes wrong. Clearing and compaction are lossy. The Anthropic article advises tuning compaction by first maximizing recall (make sure the summary keeps everything that might matter), then improving precision (cutting what turned out not to matter). For the assistant, that means a booking id or a student's stated allergy should survive a summary, while a raw 40-line calendar dump should not.

Sort it

A session history has six items. Mark each as clear (delete it) or keep in the compaction summary. (1) Student: "Is the laser cutter free Friday?" (2) A 40-line calendar result listing every booking this month. (3) Assistant: "Friday 2pm is free." (4) Student: "Book it." (5) Booking result: "confirmed, id 8841". (6) An old manual page about acrylic settings, fetched for an earlier question already answered.

Show the answers
  • Clear 2 and 6. Both are bulky raw results the model already used. Item 2 is the irrelevant-columns case: only one line of it mattered (Friday 2pm is free).
  • Keep in the summary: the student's intent (1 and 4), the key fact that Friday 2pm was free (from 3), and the booking id (5). The id is small but impossible to guess later.
  • The test for each item: could the next step fail without it? If yes, it is high-signal; if the model already extracted what it needed, clear it.

4. Between sessions: notes 3 min

The gist

When a session ends, the context is gone and the model keeps nothing. To "remember" a student, the program writes notes to a file and reads them back next time.

  • Persistent: stored outside the context so it survives after the session ends, for example in a file or database.
  • Notes: text the assistant saves for later, such as a student's training status. The article calls this structured note-taking: the agent writes notes outside the context window and pulls them back in later (Effective context engineering). Two ways to do it: the program saves and loads notes itself (the Sam example below), or the model is given a tool and decides what to write (the Memory tool, next).
  • Client-side: it runs in your program, not on the model provider's servers. The Memory tool works this way: the model asks to view or write files, and your code carries out the request and decides where the files really live (Memory tool).
  • Memory tool: a tool with file commands (such as view and create) acting on a /memories directory. Same loop as before: the model requests, the program acts. Here the model chooses what to save; in the Sam example your code chose. Either way the file lives outside the window and your program does the file work.

Example. After Sam finishes the laser cutter training, the program stores a note. Next visit, it loads the note into the context before the first call.

import json

# Saved at the end of Sam's first visit
note = {"student": "Sam", "trained_on": ["laser cutter"], "date": "2026-11-03"}
with open("sam.json", "w") as f:
    json.dump(note, f)

# Next visit: load it and put it into the system prompt
with open("sam.json") as f:
    note = json.load(f)
system_prompt = "You are the makerspace assistant. Student notes: " + json.dumps(note)
  • json.dump writes the dict to disk; that file is the persistent part.
  • json.load reads it back at the start of a new session.
  • Adding it to system_prompt puts it in the context. The model never opens the file; it only sees the text you load.
Write

Write the dict you would save for a student, Ana, who has been trained on the 3D printer but not the laser cutter, and the one line that loads it from ana.json.

Show a solution

One version: note = {"student": "Ana", "trained_on": ["3D printer"], "date": "2026-11-10"} (the date is illustrative), and the load line note = json.load(open("ana.json")). Any structure works if it records who, what and when, and the program reads it back before the first call.

Predict

A returning student says "Can I use the laser cutter?" What does the assistant say with Sam's note loaded, and without it?

Show the answer

With the note, the context contains "trained on laser cutter", so the assistant can say yes and offer to book. Without it, the model has no way to know Sam was ever trained: it will ask Sam to confirm, or send Sam to the training. Same model, same question, different answer, because of what the program put in the context.

5. Finding the right manual page 4 min

The gist

An 80-page manual does not belong in the context. Keep a short index there and fetch the one page you need, when you need it.

  • Retrieval: fetching just the relevant piece of a larger store and placing it in the context. It is lookup. Notes are different: notes are writing something down; retrieval is reading a piece back.
  • Pre-loaded: placed in the context before the model starts, on every run.
  • Just-in-time: loaded only when the model asks, through a tool call. The article describes agents keeping lightweight references and loading data when needed (Effective context engineering).
  • Identifier: a short handle for a bigger thing, like a page number, a file path or a link.
  • Trade-off, per that article: loading just-in-time is slower than having it pre-loaded, because it needs extra calls.
  • How to find the right page in a long manual (searching by meaning, splitting it into chunks) is the next lesson. Today: once you know the page, how it gets into context.

Example. The laser cutter manual has 80 pages. The assistant holds only page identifiers with titles, and a tool that fetches a page:

manual_index = {
    12: "Safety and eye protection",
    31: "Cutting acrylic: power and speed",
    47: "Cleaning the focus lens",
}

def read_manual_page(page_id):      # the tool; the PROGRAM runs this
    return open(f"laser/page_{page_id}.txt").read()
  • manual_index is pre-loaded: a few lines, always in context.
  • A question about the lens makes the model request read_manual_page(47). The program runs it and the text of page 47 joins the context for that call.
  • Only one page of 80 was loaded. The other 79 cost no page tokens (the index and the extra call still cost a little). The model picks page 47 by reading the index titles, which is why the titles must be clear.
Sort it

Sort each scenario into pre-loaded, just-in-time or notes. (1) Every chat starts with the makerspace opening hours, three lines. (2) A student asks about the focus lens and the assistant fetches page 47. (3) At the end of a visit the assistant records that Ana finished 3D printer training. (4) Every chat starts with the list of page ids and titles.

Show the answers
  • 1 is pre-loaded: tiny and needed every time.
  • 2 is just-in-time: a tool call, only when this question needs it.
  • 3 is notes: it writes something down for later. Fetching would be reading it back, which is a different step.
  • 4 is pre-loaded: it is the index that makes just-in-time possible.
One line

Which is slower, pre-loaded or just-in-time, and why?

Show the answer

Just-in-time is slower: the model must first ask, the program must fetch, and then another call happens with the page included. A pre-loaded fact is already there on the first call. You pay that delay to keep the context small and cheap.

6. Five mix-ups 2 min

The gist

Most wrong designs come from five wrong ideas. They are tempting because chatting with a model feels like talking to a person who remembers, reads everything and knows what you mean. Answer each statement, true or false, and read the reason.

Statement 1

When a student tells the assistant their name, the model itself learns it and changes.

Statement 2

Since windows can be large, the best design is to put the whole manual and every old chat in on every call.

Statement 3

Between two sessions, the model keeps nothing by itself: your program must save and reload what matters.

Statement 4

Retrieval means the model searching through its training data for the page it needs.

Statement 5

One token is the same as one word, so 1,000 words is 1,000 tokens.

7. Where it breaks 2 min

The gist

Every tool in this lesson has a cost or a failure mode. Retrieval is overkill for tiny documents, and trimmed or saved information can lose detail or go stale.

  • Retrieval can be overkill. The makerspace's safety rules are one page. Fetching it means an extra call, extra delay and a chance the model forgets to fetch. Put it in the system prompt and pay for one page of tokens each call.
  • Compaction loses detail. A summary that drops the booking id 8841 means the assistant cannot cancel that booking later.
  • Notes go stale. A note saying "trained on laser cutter" is true on the day it is written. If the training expires after a year and nobody updates the note, the assistant keeps saying "trained". The rule it gives the student is then wrong, and a person might use a machine they should not.
Fix for stale notes: store a date with every note (as in the Sam example), and have the program check it against the real training records when the stakes are safety.
Decide

The one-page safety sheet is needed in almost every conversation. Retrieve it on demand, or include it in the system prompt?

What breaks

A note says "Sam: trained" but the training expired last month. What does the assistant do wrong?

Show the answer

It confidently tells Sam to go ahead and book. The model will usually trust the note, because the note is what it sees (it could only doubt it if the program also gave it the date and the expiry rule). A stale note misleads; it does not merely leave a gap.

8. Worked example and practice 5 min

Now put it together. The rule for each item: ask is it needed on every call, only sometimes, on a later visit, or not at all? Those are the four buckets: always in context, retrieved on demand, saved between sessions, dropped. These match the section 5 labels: pre-loaded means always in context, just-in-time means retrieved on demand, and notes are the saved bucket (writing a note is the saving half; loading it back at session start is the reading half, so it is a form of retrieval too). A bucket says where an item lives between uses. "Saved" items sit in a file; the program loads them into context when a session starts, so they end up in the window too. Give each item one bucket; if an item splits (a useful fact plus bulk), split it and bucket the pieces.

Worked example

A student writes: "Can I use the 3D printer? Last visit I did the safety training." Place five pieces of information.

  1. The assistant's rules (system prompt): always in context. Every call needs them, and they are short. Without them the model would not know its job.
  2. The tool descriptions: always in context. The model can only ask for a tool it has been told about, and it needs this on every call. Keep them short, because they are paid for on every call.
  3. The 3D printer manual pages: retrieved on demand. The manual is long, and this question may need no page. Keep the page ids as an index, and fetch a page if the student asks how to load filament.
  4. The student's training status: saved between sessions. The student says they trained, but the model cannot see last visit. The program loads the saved note and checks the claim against it. If the note has no such training, the assistant says so.
  5. Old tool results (last week's calendar dump): dropped. The model already used them and they were for a different question. Keeping them adds noise and cost.

  • Last week's chat: split. The transcript itself is dropped: replaying it costs tokens on every call and mostly adds noise. If one fact mattered (for example, "trained on the 3D printer"), that fact is saved between sessions: the program should have written it to the notes at the end of that session.
  • Maintenance log: retrieved on demand. It is long, changes often, and matters only for questions like "is the printer working?". Keep an identifier for it, fetch it when asked, and do not store it in the notes, where it would go stale.

9. Summary 2 min

  • Context is everything the model sees on a call, and the window limits it. Only what is placed in it gets used.
  • Between steps the program re-sends the whole history, so each step costs more and waits longer than the last.
  • Bigger is not better: context rot means extra tokens weaken recall. Keep the smallest high-signal set; clear old tool results; compact long histories.
  • Between sessions the model keeps nothing. Notes are written by the program and loaded next time; they can go stale.
  • Retrieval fetches one page of a big store on demand. It is slower than pre-loading but keeps the context small.
  • The decision rule, per item: needed on every call, so always in context; needed sometimes, so retrieved on demand; needed on a later visit, so saved between sessions; no longer needed, so dropped.

Say it in your own words: explain to a teammate, in four sentences, why the assistant seems to "remember" a student. Say what is really remembered, where, and who put it back in front of the model.
