One row per matching pair 3 min

The gist. A join does not return one row per student. It returns one row for every pair of rows that match. If a student has three matches, that student shows up three times.

  • A one-to-many relationship: one row on one side (a student) can match many rows on the other side (their enrollments). Each enrollment belongs to exactly one student.
  • A matching pair is one row from each table whose join columns are equal. The join output has one row per matching pair (PostgreSQL tutorial, Joins Between Tables).
  • Fan-out is the name for one row on the "one" side turning into several output rows. I will use that word from here on.
SELECT s.name, e.course
FROM students s
INNER JOIN enrollments e ON e.student_id = s.student_id;
  • students s and enrollments e give each table a short alias, so s.name means "name from students".
  • ON e.student_id = s.student_id is the rule that decides which rows pair up.
  • For Ana, three enrollment rows match, so Ana appears three times: (Ana, Math), (Ana, Bio), (Ana, CS).

Walk through it like the database does. Take Ben (student_id 2): look in enrollments for rows whose student_id is 2. There is exactly one, enroll_id 4, so Ben produces one output row. Take Cy (student_id 3): rows 5 and 6 match, so Cy produces two output rows, and the name column says "Cy" on both. Nothing is wrong or duplicated in the data; the join is doing what the ON rule says.

A soccer version: a table of players and a table of match appearances. A midfielder who played 3 matches has 3 appearance rows, so a join gives you that player 3 times. Where it stops fitting: a match also has many players, which is many-to-many. That is for a later lesson.

Predicting row count: INNER vs LEFT 4 min

The gist. To predict a join's row count, count the matches each left-side row has, then add them up. INNER JOIN adds exactly the matches. LEFT JOIN guarantees every student at least one row.

  • INNER JOIN: each student contributes matches rows. A student with 0 matches contributes 0 and vanishes.
  • A LEFT JOIN keeps every row of the left table (the one written before the join keyword). If a left row has no match, it still appears once, with empty columns from the right table (PostgreSQL tutorial).
  • Those empty columns hold NULL, SQL's marker for "no value here". It is not zero and not an empty string.
  • So LEFT JOIN: each student contributes max(1, matches) rows. The 1 is the NULL-filled row for students with no matches.
-- INNER: only students that have enrollments
SELECT s.name, e.course
FROM students s
INNER JOIN enrollments e ON e.student_id = s.student_id;

-- LEFT: every student, enrollments or not
SELECT s.name, e.course
FROM students s
LEFT JOIN enrollments e ON e.student_id = s.student_id;

The only difference is the keyword. The row counts differ because of students who have no matches. To predict a count on your own, use three steps:

  1. Write each left-side row with its number of matches.
  2. Apply the rule: INNER uses matches, LEFT uses max(1, matches).
  3. Add the column up. That total is the row count, before any filter.
The 1 in max(1, matches) is only for students with no matches. A student with 3 matches contributes 3, not 4: LEFT JOIN adds no extra row when real matches exist.

Grain: what one row means 3 min

The gist. Before you count anything, ask what a single row of your result stands for. After a one-to-many join it usually stands for the many side, not the one side.

  • Grain is what one row of a table or result represents. In students, one row is one student. In enrollments, one row is one enrollment.
  • After students JOIN enrollments, the grain is one enrollment, because rows follow matching pairs. Student columns like name and tuition are repeated on every row for that student.
  • Duplicated-looking data after a join is usually this repetition rather than an error: you get a duplicated row for each match in the "many" table (Metabase Learn, duplicated data). The danger is counting or adding those repeated values as if each row were a new student.

A quick way to find the grain: ask "which column, or set of columns, would make each row unique?" In the joined result, name is not unique (Ana appears three times) but enroll_id is. Whatever is unique per row is what a row means. That unique column is also the one to count when you want to count rows of that kind.

GROUP BY changes the grain again: it merges rows that share the same value in the listed column into one row. Compare these two queries.

-- A
SELECT s.name, e.course
FROM students s INNER JOIN enrollments e ON e.student_id = s.student_id;

-- B
SELECT s.name
FROM students s INNER JOIN enrollments e ON e.student_id = s.student_id
GROUP BY s.name;
Trace it

Show the answer

A: one enrollment (6 rows). B: one student (3 rows: Ana, Ben, Cy).

COUNT(*), COUNT(column), COUNT(DISTINCT) 4 min

The gist. COUNT has three forms, and each answers a different question. Pick the one whose question matches what you want to know: rows, non-empty values, or different values.

  • An aggregate function collapses many rows into one value. COUNT is an aggregate.
  • COUNT(*) counts rows, whatever they contain.
  • COUNT(col) counts rows where col is not NULL.
  • DISTINCT removes repeated values, so COUNT(DISTINCT col) counts how many different non-NULL values col has.

The trap is a LEFT JOIN: the unmatched student produces a row, and COUNT(*) counts it. The usual fix is to count a column from the many side that cannot be NULL in a real match, such as its primary key (Ben-Gan, SQL Performance).

SELECT COUNT(*)                     AS joined_rows,
       COUNT(e.enroll_id)           AS enrollments,
       COUNT(DISTINCT s.student_id) AS students
FROM students s
LEFT JOIN enrollments e ON e.student_id = s.student_id;
  • AS joined_rows just names the output column (a column alias), the way s and e name tables.
  • COUNT(*) sees 7 rows, including Dee's NULL row.
  • COUNT(e.enroll_id) skips Dee's row, because her e.enroll_id is NULL.
  • COUNT(DISTINCT s.student_id) ignores repeats, so Ana counts once.

Soccer version: COUNT(*) is the number of lines on the appearance sheet, and COUNT(DISTINCT player) is the number of different players on it. It stops fitting at the NULL row: a real appearance sheet would have no line at all for a player who never played.

Four common mix-ups 2 min

The gist. Each of these feels reasonable until you run it on the sample tables. For each one: why it is tempting, and what is actually true.

a. "A join gives one row per student"

FROM students s INNER JOIN enrollments e ON ... returns 6 rows for 3 students. Tempting because the students table has one row each. Wrong because rows follow matches (section 1).

b. "COUNT(*) counts students"

On the LEFT JOIN, SELECT COUNT(*) returns 7, with only 4 students. Tempting because you are thinking about students. Wrong because COUNT(*) counts joined rows, and the grain is enrollment (section 3).

c. "A LEFT JOIN count shows 0 for a student with nothing"

SELECT COUNT(*) FROM students s LEFT JOIN enrollments e ON e.student_id = s.student_id WHERE s.name = 'Dee' returns 1, not 0. Tempting because Dee has no enrollments. Wrong because her NULL-filled row still exists (section 2). COUNT(e.enroll_id) would give 0.

d. "COUNT(DISTINCT e.student_id) counts every student"

On the LEFT JOIN it returns 3, not 4. Tempting because DISTINCT removes repeats. Wrong because Dee's e.student_id is NULL and DISTINCT counts only non-NULL values. Use s.student_id from the left table to include Dee.

Fixes and the check 3 min

The gist. Count the thing you mean, using the key of that thing. Then run a quick check that tells you whether the join fanned out.

  • Students: COUNT(DISTINCT s.student_id) counts each student once, however many rows they have. Without any join at all, SELECT COUNT(*) FROM students is simpler and returns 4.
  • Enrollments: COUNT(e.enroll_id) counts real enrollment rows and skips Dee's NULL row.
  • Pre-aggregate: to pre-aggregate is to collapse the many side to one row per key before joining, so the join cannot fan out (Metabase Learn).
SELECT s.name, s.tuition, c.n
FROM students s
LEFT JOIN (
  SELECT student_id, COUNT(*) AS n
  FROM enrollments
  GROUP BY student_id
) c ON c.student_id = s.student_id;
  • The inner query (the subquery) has grain one student: GROUP BY student_id gives Ana 3, Ben 1, Cy 2.
  • The outer LEFT JOIN then matches each student to at most one row, so there are exactly 4 rows and s.tuition appears once per student.
  • Dee's n comes out as NULL, not 0. Turning that into 0 is for a later lesson.

(Query B in section 3 grouped by s.name only because names are unique in our tiny table. In real data group by the id, as here, since two students can share a name.)

The check. After any join, compare COUNT(*) with COUNT(DISTINCT key) for the key of the side you meant to keep. If they differ, rows were repeated. On the INNER JOIN that is 6 against 3, so the join fanned out. That is fine if you expect it, and a bug if you did not.

Where it breaks: SUM and DISTINCT 3 min

The gist. Repeated rows hurt sums even more than counts. If a student's tuition is on three rows, adding the column adds it three times.

SELECT SUM(s.tuition)
FROM students s
LEFT JOIN enrollments e ON e.student_id = s.student_id;
  • Ana's 1000 appears 3 times (3000), Ben's 500 once, Cy's 800 twice (1600), Dee's 300 once.
  • Total: 3000 + 500 + 1600 + 300 = 5400. The true tuition across the four students is 2600 (1000 + 500 + 800 + 300).
  • Same cause as before: the grain is enrollment, so a student-level column is repeated, and adding it adds the repeats too.

Notice that nothing is "broken" in the join. The tuition column is correct on every row. The mistake is adding it at the wrong grain: tuition belongs to a student, but each row is an enrollment. The same happens with any one-side column, such as a student's age or balance. When a sum or an average looks too big after a join, count how many times each student appears before suspecting the data.

Predict the SUM

What does SUM(s.tuition) return on the INNER JOIN instead of the LEFT JOIN?

Show the answer

5100. Ana counts three times, Cy twice, Dee not at all.

The tempting fix that is unsafe

DISTINCT on a sum

SUM(DISTINCT s.tuition) removes repeated values, and on our data it returns 2600, the right total. But that is luck: all four tuitions differ. DISTINCT removes repeated values, not repeated rows. Suppose Dee paid 500 (illustrative). The true total would be 2800, but DISTINCT sees the values 1000, 500 and 800 and returns 2300, quietly dropping a real payment.

Safe fixes: sum from students alone with no join (SELECT SUM(tuition) FROM students), or pre-aggregate the many side as in section 6, so each student appears once before you add.

Check yourself

Why is SUM(DISTINCT s.tuition) unsafe?

Show the answer

It merges equal values from different students. Fix the join's grain instead of hiding the repeats.

Worked example 2 min

The gist. Four steps you can reuse on any join-and-count question: predict the rows, name the grain, choose the COUNT, check.

Worked example

Using an INNER JOIN of the four-student tables: how many students are enrolled in at least one course, and how many enrollments are there in total?

  1. Predict the rows. Matches per student: 3 + 1 + 2 + 0 = 6 rows (Dee drops out).
    Self-explain

    Why is Dee not in those rows? Because INNER JOIN keeps only matching pairs, and she has none.

  2. Name the grain. One row = one enrollment, because the rows follow matching pairs.
    Self-explain

    Why does this matter for counting students? Each student can be on several rows, so a row count is not a student count.

  3. Choose the COUNT. Enrollments is the grain, so COUNT(*) works (there is no NULL row on an INNER JOIN). Students needs COUNT(DISTINCT s.student_id).
    Self-explain

    Would COUNT(e.enroll_id) also give the enrollments? Yes, here the same 6, and it is the safer habit if you later switch to a LEFT JOIN.

  4. Check. Run this and compare it with the prediction. 
    SELECT COUNT(DISTINCT s.student_id) AS students_enrolled,
       COUNT(*)                     AS enrollments
FROM students s
INNER JOIN enrollments e ON e.student_id = s.student_id;
    Expected: 3 and 6. They differ, so the join fanned out, which matches our prediction of 6 rows for 3 students.
    Self-explain

    What would COUNT(*) alone have told you about students? Nothing correct: it says 6, which is enrollments.

Summary 1 min

  • A join returns one row per matching pair, so a "one" row fans out into as many rows as it has matches.
  • INNER rows = sum of matches; LEFT rows = sum of max(1, matches).
  • Name the grain first. After a one-to-many join it is the many side.
  • COUNT(*) counts rows, COUNT(col) skips NULL, COUNT(DISTINCT key) counts different keys.
  • Never SUM a one-side column over a fanned-out join, and do not use DISTINCT to patch it.
