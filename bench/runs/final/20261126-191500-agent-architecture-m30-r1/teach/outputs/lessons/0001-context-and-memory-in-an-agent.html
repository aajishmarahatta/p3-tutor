0. Warm-up 2 min

The gist

You already know the agent loop. This lesson is about what the model actually has in front of it each time round that loop, and what happens to it afterwards.

  • Recall from the agent-loop lesson: the model asks for an action, the program carries it out, and the result goes back to the model.
  • Picture the Friday laser cutter trace you did: "Is the laser cutter free on Friday?", then a calendar check, then an answer. This lesson extends it with a booking later on.
  • Keep that trace in mind. We will ask what the model sees at each of its steps.
Recall

In that Friday trace, a calendar result comes back. What happens next, and who actually runs the calendar tool: the model or your program?

Check your answer

The result is added to what the model reads, and the model is called again to decide the next step. The model only asks for the tool; your program runs it. If any of that felt shaky, that is fine: today's lesson keeps asking what is sent back to the model each time.

1. The context window 3.5 min

The gist

The model can only use what is written in front of it on each call. That "in front of it" space has a size limit, and it includes the reply the model is writing.

  • Token: a chunk of text, roughly a word or a piece of a word. Models read, write and are billed in tokens.
  • Context window: all the tokens the model can see in one call, including the reply it generates (Claude docs, Understanding the context window).
  • System prompt: standing instructions your program puts at the top of every call.
  • Tool definition: a written description of a tool (name, purpose, inputs). The model reads it to decide when to ask for the tool.
  • Tool result: what the tool returned, which your program puts back in front of the model.

Example: one call from the makerspace assistant, as a stack of everything in the window.

[system prompt]       You are the makerspace assistant. Be brief.
[tool definitions]    check_calendar, book_slot, read_section
[user question]       "What speed for 3 mm acrylic?"
[model reply]         (counts too, as it is written)
  • Soccer version: the coach at halftime can only plan from what is on the whiteboard. A player's injury that nobody wrote down does not exist for the plan.
  • Where it stops working: a real coach also remembers the first half. The model has no such memory; the next section shows why.

2. Nothing is kept between calls 3.5 min

The gist

The model does not remember the last call. Your program resends the whole history every step, so the window, and the cost, grows with each step.

  • Each call starts fresh. The only "memory" is the list of messages your program chooses to send again (Claude docs).
  • So the program keeps a messages list and appends every reply and every tool result to it.
  • Usage is typically billed per token. Step 4 pays again for everything from steps 1 to 3. Check your provider's pricing page for real rates; this lesson gives none.
  • The window has a limit, so a long run eventually has no room left.

Example. call_model is a stand-in for a real model call, which you have not made yet. The printed counts are made up.

messages = [system, question]
for step in range(1, 5):
    reply = call_model(messages)   # stand-in: sends EVERYTHING so far
    messages.append(reply)         # the reply joins the history
    print(step, fake_token_count(messages))  # made-up window size, reply included
    if reply.wants_tool:
        result = run_tool(reply)   # your program runs the tool
        messages.append(result)    # the result joins the history too
  • messages.append(...) is the whole "memory". Delete a line and the model forgets it.
  • Made-up output: step 1 is 1,300, step 2 is 2,950, step 4 is 3,900. Each number is the window size of that call once its reply is written, before the tool result is added. The jump at step 2 is a manual page that arrived as step 1's tool result.
Predict

The manual page arrives as the result of step 1's tool call. At step 4, how many calls have included that page?

Show the answer

Three. The page was appended after call 1, and every call after that resends the whole list: calls 2, 3 and 4.

3. Context rot, and managing context inside a session 3.5 min

The gist

A fuller window is not a better window. As it fills, the model gets worse at using it, so you trim as you go.

  • Context rot: the model's accuracy at recalling details from the window drops as the window gets longer (Anthropic Engineering).
  • Attention budget: the article's way of saying the model has a finite amount of focus to spread over everything in the window, so each extra token takes some from the rest.
  • Clearing old tool results: replace results the agent has already used with a stub, a short placeholder line. This is the lightest fix.
  • Compaction: when the window nears its limit, have the model summarize the conversation, then start a fresh window seeded with that summary.
  • Sub-agent: a helper with its own fresh context. It does a side task, then hands back only a short summary. How to design with several helpers is for a later lesson.

Example code for the lightest fix (the message shape is a simplified stand-in, like call_model):

def clear_old_results(messages, keep=2):
    results = [m for m in messages if m["role"] == "tool"]
    for m in results[:-keep]:                 # all but the newest two
        m["content"] = "[old result cleared]" # one-line stub
    return messages
  • The list stays the same length, so the conversation still makes sense, but the bulky text is gone from every later call.
  • The cost: if the agent needs a cleared result again, it has to call the tool again.
  • NBA version: at halftime the coach does not replay 24 minutes of tape. She condenses it to three points. That is compaction.
  • Where it stops working: the coach knows which three points matter. A summary can drop a detail that turns out to matter later.
Choose the tactic

Clear old results, compact, or use a sub-agent? Pick one for each case.

a. Forty calendar results, all stale, are clogging the window.

b. A two-hour chat is nearing the limit and everything in it still matters a bit.

c. The student asks a side question that means reading a long manual, but only a one-line verdict is needed.

4. Between sessions: notes 3 min

The gist

When a session ends, the window is gone. To remember a student next week, your program writes notes to a file outside the window and reads them back in.

  • This matches the short-term versus long-term framing in Lilian Weng's agent overview: short-term memory is what is in context, long-term memory is an external store.
  • Structured note-taking: the agent or program writes notes to storage outside the window and pulls them back in at later times, for example a to-do list or a NOTES.md file (Anthropic Engineering). Keeping the notes in a fixed shape, like our JSON, is this lesson's advice, not the article's.
  • The assistant needs this for each student's training status. A JSON file per student is enough.

Example. Saving a status:

import json, pathlib

def save_status(student_id, status):
    path = pathlib.Path(f"students/{student_id}.json")
    path.parent.mkdir(exist_ok=True)
    path.write_text(json.dumps(status))

save_status("s42", {"laser_cutter": "trained"})
  • path.parent.mkdir(exist_ok=True) creates the students/ folder the first time and does nothing after.
  • This design has a flaw: the note has no date. Section 7 shows the fix.
  • NBA version: a scouting report written before the game. Whoever walks in tonight reads it first and does not rely on anyone's recall. Your own NOTES.md in this workspace works the same way.
  • Where it stops working: a scout is a person with judgement. Here your program decides what is written, so a bad rule writes bad notes.
Write it

Add one function, load_status(student_id), that reads the student's file and returns {} for a student with no file yet. Try it before opening the solution.

Show a solution 
def load_status(student_id):
    path = pathlib.Path(f"students/{student_id}.json")
    if not path.exists():
        return {}                      # new student: no notes yet
    return json.loads(path.read_text())

The exists() check is the key line. Without it, a first-time student crashes the program with a file-not-found error. If yours crashed, review this section's save example, then notice what happens on a first visit.

5. Retrieval: finding the right page 3.5 min

The gist

Do not load a whole manual. Fetch only the page you need, either by searching first or by letting the agent look pages up itself.

  • Retrieval: fetching outside information into the window at the moment it is needed. It is not the model searching its own training.
  • Embedding: a numeric fingerprint of a piece of text, where texts with similar meanings get fingerprints that sit close together, like nearest neighbours in data science. No maths needed here.
  • Identifier: a short handle for a piece of content, such as a section name or file path, that lets you load it later.
  • Up-front retrieval: embed the question, find the nearest pages, put them in the window, then answer. Fast, but it must guess the right pages before the model thinks.
  • Just-in-time retrieval: the agent holds only identifiers and loads pages with a tool as it works. Slower, but it can follow up.
  • Hybrid: some content up front, the rest explored just in time. All three are described in Anthropic Engineering.

Example. The assistant gets a fourth tool, list_sections, next to read_section. The manual content is made up.

MANUALS = {"laser_cutter": {"Safety": "...",
                            "Material settings": "...",
                            "Cleaning": "..."}}

def list_sections(machine):
    return list(MANUALS[machine])          # identifiers only

def read_section(machine, name):
    return MANUALS[machine][name]          # one page, on demand
  • list_sections costs a few tokens. read_section costs one page. The rest of the manual costs nothing.
  • Data-science version: up-front is a search index that ranks documents for you. Just-in-time is opening files by path once you know the folder layout.
Trace it

A student asks: "What speed for 3 mm acrylic?" Using the two tools above, write the two or three calls the agent makes, in order, and what it does with the last one.

Show the answer
  1. list_sections("laser_cutter") returns ["Safety", "Material settings", "Cleaning"]. The agent picks the name that sounds like settings.
  2. read_section("laser_cutter", "Material settings") returns that page as a tool result.
  3. No further call. The agent answers from the page text, quoting the 3 mm acrylic row.

If you skipped the listing and guessed a name, that works only if you know the names. That is why the agent lists first. Review this section if you tried to answer without any call: the model cannot recall the makerspace's own machine settings from training.

6. Common mix-ups 2 min

The gist

Five wrong ideas tempt people here. Each one sounds reasonable, and each has a quick counterexample.

M1: the model remembers earlier steps by itself

Tempting because chatbots feel continuous. But if you remove messages.append(result), the next call has no idea the tool ran (section 2).

M2: filling a bigger window is always better

Tempting because more room sounds like more help. Made-up numbers: a manual page is 1,500 tokens. Pasting 20 pages in costs 30,000 per call, so over 5 calls that is 150,000 tokens. Reading one page costs 7,500 over the same 5 calls. More text also invites context rot (section 3).

M3: retrieval means the model searches its training

Tempting because the word sounds like recall. Retrieval fetches text from outside the model, such as your manuals. The model cannot recall your makerspace's settings, as the trace in section 5 showed.

M4: the window limits only what you send in

Tempting because the limit feels like an input cap. The reply is written into the same window, so a long reply uses up room too (section 1).

M5: memory means retraining the model

Tempting because "learning" sounds like changing the model. Our memory is just files read back in (section 4). Changing the model itself is out of scope for your mission.

True or false, with a reason

1. Notes saved to a file take up no room in the window until they are read back in.

2. If a call fits under the limit on input alone, it is safe, whatever the reply length.

3. Switching to a model with a bigger window makes long manuals cheaper to handle.

7. Where it breaks 1.5 min

The gist

Two rules above have exceptions: sometimes loading everything is right, and notes can go out of date.

  • (a) A one-page safety sheet that every answer might need should simply be loaded whole into the system prompt. Retrieval adds extra calls and a chance of fetching the wrong page, for a page that is small anyway. Retrieval pays off when content is large and only a slice is needed.
  • (b) The section 4 note "laser_cutter": "trained" has no date. If a student's training lapses, the file still says trained, and the assistant books a machine for someone who may not be allowed to use it. Notes need a date and, ideally, where the fact came from.

The fix in code: save each fact with its date and source, so it can be checked.

save_status("s42", {"laser_cutter": {
    "status": "trained",
    "date": "2026-09-14",
    "source": "training roster"}})
Spot the unsafe note

Which note is unsafe to trust when booking the laser cutter?

Show the answer

s17. A bare "trained" cannot be checked for age or origin. The dated, sourced notes can be, even when one of them says "not trained".

8. Worked example, then your turn 5 min

The gist

For each request, decide three things: what goes in the window now, what gets saved for later, and what the agent fetches when needed.

Worked example

A student writes: "Book me the laser cutter, I did training last week."

  1. Context (this session): the system prompt, the four tool definitions, the student's request, and the student's note file, read in at the start because it is small and always needed. Calendar results come in as the agent checks them. The whole manual stays out, since a booking needs none of it.
  2. Saved (between sessions): the dated status note stays in the student's file. The booking itself is not copied into notes, because the calendar already holds it, and a second copy could disagree. The claim "training last week" is not saved as fact until a staff member confirms it against the training roster; none of our four tools can read the roster.
  3. Found (just in time): if the student asks about settings, the agent calls list_sections("laser_cutter"), picks the one section that matches, such as "Material settings", and reads only that page. For a plain booking it may fetch nothing.
In contextSavedFound when needed
System prompt, 4 tool definitions, request, small status note, calendar resultsDated status note; not the bookingOnly if needed: one manual page, via list_sections then read_section

The rule of thumb: small, always-needed items go in the window (watch the cost of each call), facts that outlive the session go in a file, and big, occasionally-needed content waits to be fetched. Keep one source of truth per fact, so copies cannot disagree.

9. Summary 2.5 min

  • The model sees only the context window: everything sent in one call, plus the reply it writes.
  • Nothing carries between calls. Your program resends the history, so context and cost grow; trim it with cleared results, compaction or a sub-agent.
  • Nothing carries between sessions. Memory is notes written to a file and read back in, with dates so they can be checked.
  • Do not load a whole manual. Keep identifiers in context and fetch pages just in time, unless the content is small and always needed.
