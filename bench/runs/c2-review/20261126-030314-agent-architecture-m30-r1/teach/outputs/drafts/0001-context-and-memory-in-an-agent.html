Context and memory in an agent

By the end of this lesson you can decide, for any piece of information in the makerspace assistant, whether it lives in the model's context, in saved notes, or in a searchable manual, and say why.

Objective O3: context and memory in an agent About 30 minutes
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both are memory decisions, and each one changes answer quality and your model budget. You will have to defend these choices at your design review.

Warm-up 2 min

Recall

From the agent loop: when the assistant calls the booking tool, who actually runs it, the model or your program? And is the next step a new model call or a continuation of the old one?

Check your answer
  • Your program runs the tool. The model only writes a request for it.
  • Each step is a separate model call. That is exactly why "what does the model see on each call?" is the question of this lesson.

The context window 4 min

  • The model only knows what is in the text you send it on this call.
  • That text has a size limit and a price. Both matter for your assistant.
  • A token is a chunk of text, often a word or part of a word, that the model reads and writes. Limits and prices are counted in tokens, not characters.
  • The context window is everything the model can see when it writes a response, including the response itself. Anthropic's docs call it a "working memory" for the model (Claude docs: Context windows).
  • It holds more than the chat. Everything below counts toward the limit:
    • the system prompt, the standing instructions you write, such as "you are the makerspace assistant",
    • every earlier message, including tool results, the text a tool returns to the model,
    • the tool descriptions, short texts telling the model what each tool does and when to call it,
    • the model's own output.
  • Scale: current Claude models have windows from 200k up to 1M tokens, depending on the model. A 200-page manual is very roughly 100k tokens (my own rule-of-thumb estimate, not a figure from the docs: use a token counter for real numbers), so it may fit and still be a bad idea.
  • At the limit the request cannot hold more: you must trim or summarise before the next call, or the call fails.
  • Cost follows the window: you pay for the tokens sent, and the history is sent again on every call. Output tokens are billed too. Prompt caching (the provider stores the unchanged start of your prompt, so repeating it is billed at a discount) lowers the price, but cached tokens still occupy the window: "not whether they count" (Claude docs).

Which of these does NOT count toward the context window on a call?

What is kept between steps 5 min

  • The model remembers nothing from the previous step. Your program resends the whole history every time.
  • So the window grows with every tool call, and so does the cost of each next step.
  • The model does not keep a hidden state between calls. The docs say each user message and assistant response accumulates in the window and earlier turns are preserved completely, because they are sent again (Claude docs).
  • In the agent loop, "memory between steps" is just a Python list your program keeps, called the message history. Each step appends the model's request and the tool's result, then sends the whole list.
  • The post on context engineering says the same of agents: a loop produces more and more data that could matter for the next turn, so it must be refined over time (Anthropic: Effective context engineering).

Here is a runnable stand-in. It counts words instead of tokens, the "calendar" result is fake, and the real API's message format differs a little (for instance, the system prompt is passed separately). You do not need a model to see the growth:

history = [{"role": "user", "content": "Is the laser cutter free Friday?"}]

def size(msgs):                      # crude stand-in for a token count
    return sum(len(m["content"].split()) for m in msgs)

for step in range(3):
    print("step", step, "sends", size(history), "words")
    history.append({"role": "assistant", "content": "call check_calendar(...)"})
    history.append({"role": "tool", "content": "calendar row " * 50})
  • history is the only memory. If you forget to append, the model forgets.
  • size(history) is what each call sends. Output: 6, then 108, then 210 words.
  • The big tool result is paid for again on every later step, even though only step 1 needed it.
Analogy from data science: each call is like re-running a whole notebook from the top instead of keeping a kernel alive. Nothing carries over except what the file contains. It stops working because a notebook's cost is time, while here you also pay per token.

When the window gets crowded 4 min

  • A fuller window is not just pricier: the model also recalls details worse as it fills.
  • You manage this by dropping what is no longer needed, or by summarising.
  • Context rot is the drop in accuracy and recall as the token count grows. The Claude docs state that more context isn't automatically better. The engineering post calls context a finite resource with diminishing returns, and describes a gradient, not a hard cliff (Anthropic).
  • Goal: the smallest set of high-signal tokens that gets the job done.
  • Two standard fixes:
    • Clearing old tool results: delete the bulky output of a past tool call once its answer was used. The post calls this one of the safest, lightest-touch forms of trimming.
    • Compaction: summarise the conversation so far and start a fresh window with the summary. The post says to keep decisions and unresolved problems and drop redundant tool output.
  • Trade-off: both lose detail. A summary can drop the one fact you needed later.

Example: the calendar tool returns 40 rows. The model reads them, finds Friday 2 pm free, and books it. After that, the 40 rows are dead weight. Replace them with one line, "Checked calendar: Fri 2 pm free, booked." and every later call is cheaper.

Analogy: compaction is the halftime report. The coach does not replay the 45 minutes; the team gets the three things that matter for the second half. The risk is the same too: a bad report loses the detail that mattered.

What is kept between sessions: notes 5 min

  • When a session (one conversation, one history list) ends, the history is gone. Nothing survives unless your program saves it.
  • Notes are text the agent writes to storage outside the window, then reads back next time.
  • A session is one conversation with one history list, from first message to the end. A new visit by the same student starts a new, empty list.
  • Persistent memory is therefore a file or database that your program writes to and reads from. Anthropic describes agents that regularly write notes persisted outside the context window, such as a to-do list or a NOTES.md file, and pull them back in later (Anthropic).
  • Analogy from data science: the window is RAM and notes are disk. RAM is fast and visible to the running program but wiped on exit. Disk survives but must be loaded to be used. The analogy breaks here: loaded notes also cost tokens and can rot the window.
  • So decide deliberately what to save: facts that will matter next visit, written short.
from pathlib import Path

def read_notes(student):
    p = Path(f"notes/{student}.md")
    return p.read_text() if p.exists() else ""

def save_note(student, line):
    Path("notes").mkdir(exist_ok=True)
    with open(f"notes/{student}.md", "a") as f:
        f.write(line + "\n")

save_note("jo", "Passed laser cutter safety course 2026-11-03")
system_prompt = "Student notes:\n" + read_notes("jo")   # sent with the next session's first call
  • save_note appends one line to a per-student file. It is plain Python, with no model involved.
  • read_notes returns an empty string for a first-time student, so the code never crashes.
  • The last line puts the notes into the next session's starting context. That load step is what makes it "memory".
  • You can also let the model decide what to save by giving it a "save note" tool. Anthropic offers a file-based memory tool in this style, where the model asks and your app does the reading and writing (Anthropic: Context management).

Retrieval: finding the right manual page 5 min

  • A 200-page manual may not fit, and even where it fits it should not ride along on every call: it costs tokens each time, crowds out other content and hurts recall.
  • Retrieval means searching the manual and loading only the few passages that match the question.
  • Retrieval is fetching relevant information from outside the window and placing it into the window just for this step. The manuals become a store the assistant searches, not text it carries.
  • Typical set-up, in order:
    1. Split each manual into chunks, passages of a few paragraphs, ideally cut along section headings.
    2. Build an index, a lookup structure prepared in advance so a query can find the best few chunks fast. Two common ways follow.
      • Keyword search ranks chunks by how many of the query's words they contain.
      • Embedding search turns each chunk into a list of numbers that captures its meaning; nearby lists mean similar meaning.
    3. At question time, the assistant calls a search tool, such as search_manual(query), and gets back the top few chunks.
    4. Those chunks enter the window as a tool result. The model answers from them.
  • This is the "just in time" pattern from Anthropic's post: keep small references (file names, saved queries) and load the data behind them only when needed, instead of preloading everything. Its stated cost is that runtime exploration is slower than pre-computed data (Anthropic).
  • Keyword search wins on exact strings like a machine model or an error code. Embeddings win when the student's words differ from the manual's ("it keeps burning the edges" vs "reduce power to prevent charring"). Combining both is common.

A runnable toy keyword search over three chunks:

chunks = [
    "Laser cutter: replace the lens by unscrewing the nozzle ring.",
    "Laser cutter: acrylic 3 mm, power 40 percent, speed 20.",
    "3D printer: clean the nozzle with a cold pull.",
]

def search(query, k=1):
    words = set(query.lower().split())
    def score(chunk):                       # count shared words
        return len(words & set(chunk.lower().split()))
    return sorted(chunks, key=score, reverse=True)[:k]

print(search("how do I replace the laser lens"))
  • score counts words shared by the query and a chunk. Chunk 1 shares four (laser, replace, the, lens), chunk 2 one, chunk 3 one.
  • The program prints chunk 1 only, and that string is what would go into the window as a tool result.
  • It is crude: it counts "the" like any word, and it would miss "swap the optic". That gap is what embeddings address.
Analogy: retrieval is a scout pulling every corner kick from a season of match footage instead of watching all 38 games. It fails when the query is vague: "good chances" returns noise, and so does a vague manual search. Chunks can also fail alone: "set it to 40%" loses its machine and material when cut out, which is why chunks are cut along headings (see Contextual Retrieval under Go further for a fix).

Common mix-ups 2 min

Mix-up 1: "The model remembers me"

Tempting because a chatbot feels like one continuous mind. In fact each call is stateless: it keeps nothing from earlier calls and sees only the text sent. In the code above, the model's "memory" is the history list; drop an append and that content is never sent. Across sessions, no saved note means no recall.

Mix-up 2: "A bigger window removes the need for retrieval and notes"

Tempting because some models have very large windows. But you pay for every token on every call, and recall degrades as the window fills (context rot). A window also resets between sessions, however large. Retrieval and notes stay useful at any window size.

Mix-up 3: "Retrieval means the model searched its own memory"

Tempting because the answer comes back as fluent text. The search is a tool your program runs, over text you indexed. If the right chunk is not returned, the model cannot see it, and it may then answer from training patterns and sound sure. Check the retrieval first when answers are wrong.

A second look, where notes fail: notes go stale. If a note says "Jo is certified on the laser" and the certification expires, the assistant will trust it. For facts that change, such as bookings or training status, store the record of truth in a database, let a tool read it, and keep the note as a pointer or not at all.

Worked example and practice 6 min

Worked example: the laser cutter

Jo asks: "What power for 3 mm acrylic, and book me Friday 2 pm." Sort each item into window, notes, or retrieval, and say when it is cleared or loaded.

  1. "Be concise, always check training before booking." Short and needed every call. System prompt, always in the window.
  2. "Jo passed laser safety on 2026-11-03." A fact about Jo needed on later visits. Saved as a note, loaded at session start. Because training status can change, the booking tool should still verify it against the real record.
  3. The 120-page laser manual. Large and needed only for some questions. Retrieval: search "3 mm acrylic power", load the top chunks only.
  4. The 40-row calendar result. Needed for one decision. It sits in the window until the booking is made, then clear it down to "Fri 2 pm booked".
  5. "Jo prefers Friday afternoons." New and useful next time. Save as a note at the end of the session.

The test applied each time: how often is it needed, how big is it, and does it have to outlive the session?

Your turn: the 3D printer

Sam asks how to fix the print bed not sticking, then asks to book a printer on Saturday. Sort each item as window, notes or retrieval, with a one-line reason. Item 1 is done: "Never book without checking training": system prompt, in the window always, because it is short and needed on every call.

  1. The 3D printer manual, 150 pages.
  2. "Sam completed printer training on 2026-10-20", written as a note last month. Today the training office's record shows Sam's certification was revoked on 2026-11-10. Sam asks for a booking. What should the assistant do, and why?
  3. A 60-row printer availability table, returned at step 3. Write the one-line replacement you would leave in the history after booking.
  4. The search for "bed not sticking" returns two chunks about resin printers, but the makerspace has only filament printers. What do you check first, and what does the assistant say meanwhile?
Show a solution
  1. Retrieval. Large and question-specific. Search "bed adhesion" and load only the hits.
  2. The note can be stale. Training status changes, so treat the note as a hint and have the booking tool read the real record before booking. Store changing facts in the real training and booking database and read them with a tool, not only in notes.
  3. Window, then cleared. Example: "Checked printers: Sat 10 am free, booked for Sam." The rows were needed to pick a slot and are dead weight after.
  4. Check retrieval first: the query wording, the chunks and the index (are resin and filament manuals mixed?). Meanwhile the assistant should say the manual excerpts did not match, not answer confidently from them.

Summary 1 min

  • The context window is all the text the model sees on one call. It has a limit, a price, and quality that drops as it fills.
  • Between steps, memory is your message history, resent every call, so tool results keep costing until cleared or summarised.
  • Between sessions, nothing survives unless saved: notes in storage, loaded into the next window.
  • Retrieval searches big stores, such as manuals, and loads only the best chunks.

Say it in your own words: without looking up, explain to a teammate why the assistant should not just paste all the manuals into the system prompt, and name what you would do instead for the manuals and for each student's training status.
