Context and memory in an agent

By the end of this lesson you can say what the makerspace assistant keeps in its context at each step, what it saves between sessions, and how it finds the right page in a long manual.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (learning record 0002)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both jobs are memory jobs, and both cost money: every token the model reads is a token you pay for. This lesson gives you the vocabulary and the decisions to defend at your design review.

Check your answer

The model is called and asks for an action (a calendar lookup). Your program runs the tool and sends the result back. The model is called again, and this repeats until the model writes a final answer or a limit is hit. Your program runs the tool; the model only asks. Keep that in mind: "what does the model see on each call?" is exactly today's question.

The context window 4 min

The context window is the model's whole view of the world on one call. If it is not in the window, the model cannot use it. The window is limited, and you pay for what you put in it.

  • A token is a small chunk of text, often a word or part of a word. The model reads and writes tokens.
  • The context window is all the text the model can reference when it writes a response, including the response itself (Claude docs: context windows).
  • The docs call it working memory, and it is separate from training data. Training gave the model patterns; the window holds this task's facts.
  • Everything counts toward it: the system prompt (your standing instructions), the messages, the tool definitions, the tool results, and the output.
  • It has a size limit, and it also has a quality limit. As the token count grows, the model's accuracy at recalling information from the window drops. Anthropic calls this context rot, and describes an attention budget: every new token uses up a bit of the model's ability to focus (Anthropic: effective context engineering).
  • The goal is therefore the smallest set of high-signal tokens that gets the job done, not the biggest pile of text that fits.

Analogy. Think of the window as a soccer coach's whiteboard at halftime. It is the only thing the players look at. A board crammed with forty arrows is worse than one with three clear instructions. Where it breaks: a whiteboard can be erased and rewritten for free, but every token on this board is billed.

A common mix-up

"The context window is how much the model knows." It is tempting because a bigger window sounds like a smarter model. Wrong: the window is only what is in front of the model right now. A fact the model learned in training is not in the window, and a fact in the window can still be missed once the window is long and noisy.

Between steps: the history grows 5 min

The model keeps nothing between calls. Your program keeps the conversation and re-sends all of it each step. So each step's input is longer than the last, and the total bill grows faster than the number of steps.

  • Each call to the model is independent. The model has no hidden memory of the previous call.
  • What looks like memory within a task is your program appending to a list, then sending the whole list again.
  • This is the "program runs the loop" idea from last time, applied to memory.
  • You are billed on the tokens you send, so a long tool result is paid for again on every later step. Caching can lower the price of re-sent tokens, but it does not change whether they count toward the window (context windows docs).

Here is the idea as runnable Python. There is no model in it: fake_model stands in so you can watch the history grow. As a data-science analogy, it is like appending rows to a DataFrame and re-scoring the whole table after each new row.

history = [{"role": "user", "content": "Is the laser cutter free Friday?"}]

def fake_model(messages):
    # A real model reads ALL of messages every time it is called.
    print("model sees", len(messages), "messages")
    if len(messages) < 3:
        return {"role": "assistant", "content": "CALL calendar(laser, Friday)"}
    return {"role": "assistant", "content": "Free 2-4 pm."}

while True:
    reply = fake_model(history)          # step 1: call the model
    history.append(reply)                # step 2: keep its reply
    if reply["content"].startswith("CALL"):
        result = "Friday: booked 9-12 and 4-6"        # your program runs the tool
        history.append({"role": "user", "content": result})  # step 3: append result
    else:
        break
  • history is the only memory. If you delete the list, the "conversation" is gone.
  • fake_model(history) receives the whole list each time. Run it: it prints 1 message, then 3.
  • The tool result is appended as a message, so the model sees it on the next call and every call after.
A common mix-up

"The model remembers the earlier steps because it just did them." Tempting, because the answer at step 4 does use step 2's result. But that works only because your program put step 2's result back in the input. Drop it from history and the model has no trace of it.

Between sessions: nothing survives 3 min

A session is one conversation or task. When it ends, the window is gone. Anything the assistant should know next time must be saved outside the window and loaded back in by your program.

  • A session is one run of the assistant, from a student's first message to the end of the conversation.
  • Next week, a new session starts with an empty history. The model cannot know that Dana finished laser training in October.
  • So the memory that crosses sessions is not in the model. It lives in your storage: a file, a database, a calendar. Your program reads it and puts the relevant part in the next window.
  • Two things persist, in two different ways: facts about the world (the booking calendar, already a tool) and facts about this user or task (training status, preferences).

Analogy. An NFL team's playbook is the same every week, but the game plan for Sunday is built from the film of last week's opponent. The film lives in the team's files, not in the players' heads on game day. Where it breaks: players remember on their own; the model never does.

Check yourself

Dana tells the assistant on Monday: "I'm left-handed, so show me the left-hand setup." On Friday she opens a new chat. Why does the assistant ask again?

Show the answer

Nothing from Monday was saved or loaded. A fresh session has only what your program puts in the window.

Notes as memory 5 min

Notes are small pieces of text the agent writes to a file or database on purpose, then reads back later. They are how you give an agent memory across sessions, and they keep long tasks from filling the window.

  • Structured note-taking (also called agentic memory) means the agent writes notes outside the window and pulls them back in later, like a NOTES.md file or a to-do list (Anthropic).
  • Claude's memory tool is one version: the model asks to view, create, edit or delete files in a /memories directory, and your application performs those actions on storage you control (memory tool docs, in Spanish). It is the same loop as before, with files as the tool.
  • The docs also say your handler must reject any path that escapes the memory directory, such as /memories/../../secrets.env. A student must never be able to read another student's file.
  • Good notes are short, factual and about stable things: training status, preferences, "task half done, next step is X".
import json, pathlib

NOTES = pathlib.Path("notes")
NOTES.mkdir(exist_ok=True)

def save_note(student_id, facts):          # your program writes the file
    (NOTES / f"{student_id}.json").write_text(json.dumps(facts))

def load_note(student_id):                 # your program reads it next session
    path = NOTES / f"{student_id}.json"
    return json.loads(path.read_text()) if path.exists() else {}

save_note("dana", {"laser_trained": "2026-10-14", "hand": "left"})

# Next session: build the first window from the note
facts = load_note("dana")
system_prompt = "You are the makerspace assistant. Student facts: " + json.dumps(facts)
  • save_note and load_note are ordinary Python. The model never touches the disk: it asks, and your code does it.
  • The last line is the whole trick. The note becomes part of the next window, a few dozen tokens instead of a whole old chat.
  • In a real agent you expose save_note as a tool the model can call, and write its description clearly (that is a later lesson).
A common mix-up

"Just save the whole chat and reload it." Tempting because it is simple and loses nothing. But it re-pays for every old token on every call, fills the window with stale detail, and can bury the one fact that matters. Notes are valuable because they are a selection.

Retrieval as memory 5 min

Retrieval means fetching only the few pieces of a big collection that this question needs, and putting just those in the window. It is how the assistant can "know" fifty manuals without paying to read them all on every call.

  • Say the manuals total 400,000 tokens. Putting all of it in every call would be slow, expensive and subject to context rot.
  • Retrieval splits the manuals into chunks (page-sized pieces), finds the chunks most relevant to the question, and puts only those in the window.
  • Two common ways to find them: keyword search (match words, like grep), and embedding search (turn each chunk and the question into a list of numbers, then pick the chunks whose numbers are closest, so "bed won't stick" can match "first-layer adhesion").
  • Anthropic describes just-in-time retrieval: the agent keeps lightweight pointers (file paths, stored queries) and loads content with tools at runtime, instead of loading everything up front. The tradeoff is that runtime exploration is slower than pre-loaded data (Anthropic).
  • In this setup retrieval is just another tool in the loop: search_manuals("laser cutter focus") returns three chunks, which are appended to the history.

Analogy. A scout does not watch every minute of every game in a league. They pull the clips for one player. Retrieval is the clip pull. Where it breaks: if the clip tagging is bad, the scout misses the key play and does not know it.

A second look: where retrieval fails

  • Wrong chunks. A question like "why does my cut look burnt?" may retrieve the safety chapter instead of the speed settings. The model then answers confidently from the wrong page.
  • Answer spans many chunks. "Compare all three printers" needs content from several manuals at once.
  • Fixes. Return the source page with each chunk so answers can be checked. Let the agent search again with different words. For a short fixed list, such as three machine rules, skip retrieval and put it in the system prompt.

When context gets too big 3 min

Long tasks can fill the window even with good notes and retrieval. Three tools trim it: clear old tool results, summarize the history (compaction), or hand a sub-task to a fresh window.

  • Clearing tool results: drop the bulky output of an old tool call, since the model can call the tool again if it needs it. Anthropic calls this one of the safest, lightest-touch forms of compaction.
  • Compaction: when the conversation nears the limit, summarize it and start a new window with the summary. The risk is that a detail you needed was left out of the summary.
  • A sub-agent is a second model loop with its own clean window. It may read tens of thousands of tokens, then return a summary of often 1,000 to 2,000 tokens to the main agent.
  • Which to use is a judgment call, and you will return to sub-agents in a later lesson on splitting work across agents.
For the makerspace assistant, most requests are short: a question, one or two tool calls, an answer. Do not build compaction on day one. Measure the token counts first and add it only when real sessions get long.
A common mix-up

"A million-token window means I do not need memory design." Tempting, because it feels like the problem is solved. But a big window still empties at session end, still bills every token, and still suffers context rot. Window size sets the limit; it does not choose what to put in.

Worked example and practice 8 min

Worked example

Dana, a returning student, asks: "Can I cut 3 mm acrylic on the laser on Friday afternoon? I did training in October." Decide what is in context, what is retrieved and what is saved.

  1. Start of session (load notes). The program loads Dana's note and adds a line to the system prompt: laser trained 2026-10-14, left-handed. Reason: the training status decides whether she may book, and it must survive between visits.
  2. Call 1. Window: system prompt, three tool descriptions, Dana's question. The model asks for search_manuals("laser acrylic 3mm settings"). Reason: the settings are shared reference text, so they are retrieved, not stored in the prompt.
  3. Call 2. The program ran the search and appended three chunks (about 900 tokens). The model asks for calendar("laser", "Friday"). Reason: availability changes daily, so it is fetched live and never saved.
  4. Call 3. The window now holds the prompt, question, both tool calls and both results. The model writes the final answer: settings from the page, and a free 2 to 4 pm slot. It also asks to book it; Dana confirms.
  5. End of session (save notes). The program saves one new line: "booked laser Fri 2 pm; first acrylic job". It does not save the chunks or the chat. Reason: the next visit needs the fact, not the transcript.

Each kind of information found a different home: stable facts about Dana went to notes, shared manual text was retrieved on demand, live availability came from a tool, and the rest disappeared with the window.

Reflection

Your design review lead asks: "Why not just give the model the whole chat history and all the manuals every time?" Write a three-sentence answer using cost, context rot and sessions.

Show a model answer

Every token in the window is billed on every call, so sending all manuals and all history multiplies our model budget. A long window also lowers the model's accuracy at finding the one fact that matters (context rot). And none of it survives past the session anyway, so we still need saved notes for facts like training status, plus retrieval for the manuals.

Summary 2 min

  • The context window is everything the model sees on one call: prompt, tools, messages, results and reply. It is limited and billed.
  • Between steps, your program keeps the history and re-sends it all each call, so cost grows with every step.
  • Between sessions, nothing survives unless you save it outside the window and load it back.
  • Notes hold small stable facts about a user or task. Retrieval pulls a few chunks from large shared text.
  • When the window fills, clear old results, compact, or use a sub-agent, but measure first.
