Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what stays in context, what is saved between sessions, and what is retrieved from the manuals, and say why.

Objective O3: context and memory in an agent About 30 minutes Builds on: what a language model does, and the agent loop
Why this matters for you

Your assistant has to answer from long machine manuals and know each student's training status on the next visit. It also has to do both on a small model budget. Those are three design decisions: keep, save, find. This lesson gives you the rules for making them.

Warm-up 2 min

The gist: an agent answers by looping: ask for an action, get a result, repeat. Today is about what the model has in front of it at each pass.

A student asks: "Is the laser cutter free Friday?" The assistant answers by looping, and you already know the loop.

Recall

Check your answer

(1) The model asks for an action, for example check_calendar(machine="laser", day="Friday"). (2) Your program, not the model, runs it. (3) The result, say "free 2-4 pm", goes back to the model, which then asks for another action or writes the final answer. A language model takes text in and writes text out, piece by piece.

Today's question: when the result comes back, what exactly does the model see? Everything it sees is its context, and managing it is half of agent design.

Tokens and the context window 3 min

The gist: the model can only use text that is in front of it during a call. That space has a size limit, and you pay for every piece of text that fills it.

  • Token: a chunk of text the model reads or writes, roughly a word or a piece of a word. How many tokens a text takes is a rough rule that varies by model and language.
  • Cost per token: providers bill by tokens, for what you send and what the model writes. Tokens are what your sponsor's budget is spent on.
  • Context window: all the text the model can reference when generating a response, including the response itself (Claude Platform docs, Context windows). Each model has a maximum size.

Sports picture: the window is the coach's whiteboard at halftime. The coach can use only what is written on it, and the board has a fixed size. Where it stops working: a coach also remembers last season, and the model has nothing like that.

What sits on the whiteboard for the makerspace assistant:

  • System prompt: fixed instructions sent at the start of every call ("You are the makerspace assistant...").
  • Tool definitions: the name, description and inputs of each tool the model may call.
  • The chat history so far, the results of tools, and the model's own reply.
LIMIT = 4_000   # illustrative; real limits depend on the model

window = {      # rough token counts, made up for illustration
    "system prompt": 300,
    "tool definitions": 700,
    "chat history": 900,
    "tool result (manual page)": 1500,
    "model's reply": 200,
}
used = sum(window.values())
print(used, "of", LIMIT, "tokens used")   # 3600 of 4000 tokens used
  • window is a plain dict: each part of the call and its size.
  • sum(window.values()) is the number the limit applies to, and the number you are billed for.
  • One manual page took more room than the system prompt and tool definitions together.

Nothing is kept between calls 3 min

The gist: the model carries nothing from one call to the next. At each loop step your program sends the whole history again, so the window and the bill keep growing.

  • A call is one request from your program to the model, which returns one reply. Each loop step is one call.
  • Per the docs, each turn's input is all the prior history plus the new message (Context windows).
  • So "the conversation" is just a list your program keeps and re-sends. It is like a list you append to and then reprocess from index 0 every time.
def approx_tokens(text):
    return len(text) // 4          # rough, approximate rule of thumb

history = ["x" * 4400]                  # ~1,100 tokens: system prompt + tools + question
total_billed = 0
for step in range(1, 6):
    if step > 1:
        history.append("x" * 3200)       # ~800 tokens: the previous step's tool result
    sent = sum(approx_tokens(m) for m in history)       # everything re-sent
    total_billed += sent
    print(step, sent, total_billed)
# prints: 1 1100 1100 / 2 1900 3000 / 3 2700 5700 / 4 3500 9200 / 5 4300 13500
  • history is the list your program keeps; the model keeps none.
  • sent is recomputed from the whole list each step: that is the call's input size.
  • total_billed adds every step's sent. You pay for the sum, not the last number.

Illustrative numbers for Figure 2: 1,000 tokens of system prompt and tool definitions, a 100-token question, and an 800-token tool result added before each later call. The model's own replies are ignored to keep it simple.

Cost note for your budget: without any savings tricks, each step costs more than the one before, so a loop that takes twice as many steps costs more than twice as much. Providers offer prompt caching, which makes repeated text cheaper to re-send, but cached text still occupies the window (Context windows). Caching lowers the price, not the size, so rot and limits still apply. Check your provider's pricing before you quote savings.

Keeping the window useful 3 min

The gist: a fuller window is not a better window. Keep what helps with the next step, and drop or shrink the rest.

  • Context rot: as the number of tokens in the window grows, the model's ability to recall information from it decreases. Anthropic ties this to a limited "attention budget" that every added token draws on (Effective context engineering for AI agents).
  • The aim is the smallest set of high-signal tokens that makes the next step go well.
  • Clear old tool results: once the model has used a result, the raw text can go.
  • Compaction: when the window nears its limit, the model summarizes the history and the conversation restarts from that summary.
  • Sub-agent: a second agent that does a focused job in its own fresh window and hands back a short summary. Later lessons cover when this pays off.

Sports picture: at halftime a coach gives a two-minute recap, not a replay of the first 45 minutes. That is compaction. It stops working where a coach knows which details matter for the second half, whereas a model's summary can silently drop a detail you needed later.

def clear_old_tool_results(history, keep_last=1):
    tool_idx = [i for i, m in enumerate(history) if m["role"] == "tool"]
    for i in tool_idx[:-keep_last]:                  # all but the newest
        history[i]["content"] = "[old tool result cleared]"
    return history

def compact(history, summarize):
    summary = summarize(history)                     # one extra model call
    return [history[0],                              # keep the system prompt
            {"role": "user", "content": "Summary so far: " + summary}]   # a sketch
  • Here history is a list of dicts like {"role": "tool", "content": "..."}, the usual shape for a real conversation (Section 2 used bare strings to keep the sizes simple). Use keep_last of 1 or more.
  • tool_idx[:-keep_last] picks every tool result except the newest few; their text is replaced by a stub.
  • compact returns a two-item history: the system prompt, then the summary. The summary replaces everything else.

Clear 2 and 3. Both are bulky tool results the model has already used. Message 4 holds what mattered from them (the free slot and the start steps).

If you cleared 4 or 6, you would lose the short, high-signal parts. If you kept 2 and 3, you would pay for them again at every later step (Section 2).

Memory between sessions 3 min

The gist: when a new session starts, the window starts empty. If the assistant should know something tomorrow, your program has to save it and load it again.

  • A session is one conversation with a student, from the first message to the end.
  • Notes (also called memory) are information your program writes outside the window, in a file or database, and reads back in later.
  • Anthropic calls the agent version structured note-taking: the agent writes notes to storage outside the window, such as a NOTES.md file or a memory tool, and pulls them back in later (Effective context engineering).
  • Save facts that matter next time, such as training status, with a date. Do not save whole transcripts.

Sports picture: the scouting binder. The whiteboard is wiped after the game, but the binder stays in the office and the coach reads the relevant page before the next one. Where it stops working: a human coach reads the binder by habit, while your program must load it on purpose.

import json

def save_status(student_id, status, path="students.json"):
    try:
        with open(path) as f:
            data = json.load(f)
    except FileNotFoundError:
        data = {}
    data[student_id] = status                 # overwrite this student's record
    with open(path, "w") as f:
        json.dump(data, f, indent=2)

save_status("s123", {"trained": ["laser cutter"], "prefers": "afternoons",
                     "as_of": "2025-10-03"})
  • The file is a JSON dict keyed by student id, which you already know how to read.
  • This runs in your program, not in the model: the model never touches the file unless a tool lets it.
Check yourself: write it

Write load_status(student_id) in two or three lines. It returns that student's record from students.json, or an empty dict if that student is not in the file. (Bonus: also cover a missing file.) Then say where the result should go at the start of a session.

Show a solution 
def load_status(student_id):
    with open("students.json") as f:
        return json.load(f).get(student_id, {})

.get(student_id, {}) gives a new student an empty record instead of a crash. The result goes into the system prompt (or the first message), for example "...Student record: " + json.dumps(load_status("s123")). It is saved outside the window and has to be put back in each session.

Bonus, a missing file: open raises FileNotFoundError when students.json does not exist yet, the case save_status handled. The full version:

Retrieval: find the page, do not paste the book 4 min

The gist: machine manuals are far too long to put in every call. Split them up, search for the few pieces that match the question, and put only those in the window.

  • Chunk: a short piece of a long document, such as one paragraph of a manual.
  • Keyword search: score each chunk by the query's words it contains. The standard version, BM25, builds on a scheme (TF-IDF) that favors distinctive words, and also adjusts for chunk length (Contextual Retrieval). The score below is a simplified stand-in that only counts shared words.
  • Embedding: a list of numbers that captures the meaning of a text, so texts with similar meanings get similar numbers. Search by embedding can match "heat" with "temperature". We will not look inside.
  • Top-k: keep only the k best-scoring chunks. Only those enter the window.

Sports picture: the film room. You do not watch every game; you search for "third-down plays" and watch those clips. Where it stops working: a film index was made by people, and a poor search quietly returns the wrong clips.

chunks = [   # invented sample manual
    "Safety: wear eye protection at the laser cutter.",
    "Level the print bed before each print on the 3D printer.",
    "Clean the nozzle with the brass brush after the temperature drops.",
    "Laser cutter power for 3 mm acrylic is 60 percent.",
    "PETG prints at a nozzle temperature of 230 C on the 3D printer.",
]

def score(query, chunk):
    words = set(chunk.lower().replace(".", "").split())
    return len(set(query.lower().split()) & words)    # shared words

def top_k(query, chunks, k=2):
    return sorted(chunks, key=lambda c: score(query, c), reverse=True)[:k]
  • score counts shared words, which is keyword search at its simplest.
  • top_k sorts by score and cuts to k. It always returns k chunks, even when the second one barely matches.
Two ways to load: pre-load the data before the call (what top_k does), or load it just-in-time: the agent keeps lightweight identifiers such as file paths and fetches the content with a tool only when needed (Effective context engineering). For example, the prompt lists manuals/laser.txt, and the model calls read_file("manuals/laser.txt") only when a question needs it.
Check yourself: predict

With the code above, top_k("petg temperature", chunks) runs. Which chunk comes first, and why?

Show the answer, and the synonym trap

The PETG chunk scores 2, the cleaning chunk 1, the rest 0, so the top 2 are PETG and cleaning.

Now the query "extruder heat" gets 0 for every chunk, so keyword search returns the first two in the list and misses the PETG chunk, even though it is the answer. It uses different words for the same idea. An embedding search can match them on meaning, which is why real systems often use both (Contextual Retrieval).

Common mix-ups 2 min

The gist: five tempting ideas about agent memory are wrong. Each has a quick test.

Five common mix-ups
  • "The model remembers us by itself." Tempting because chatbots feel continuous. But start a new session and ask "what is my training status?": with nothing loaded, the model has no idea (Section 4).
  • "A bigger window means no need for memory or retrieval." Tempting because "it all fits". But you still pay for every token at every step, and recall gets worse as the window fills (Sections 2 and 3).
  • "More context is always better." Tempting because more information sounds safer. But the laser manual in a question about the 3D printer adds cost and distraction, and nothing else.
  • "The model reads the whole manual." Tempting because the answers sound informed. But it sees only the chunks your code put in the window (Section 5).
  • "Memory lives inside the model." Tempting because the model is the part that talks. But what looks like memory is your program's files plus whatever it chose to load into this call.
Check yourself: true or false

Yesterday the assistant told Sam the laser cutter's rules. Today's new session starts out knowing that.

If the window could hold the whole 400-page manual, retrieval would be pointless.

When the model answers a manual question, it has seen only the chunks that your code placed in the window.

Where it breaks 2 min

The gist: retrieval can fetch the wrong chunk, and a chunk cut out of its page can lose the context that gave it meaning.

  • Imagine a chunk that says only "Step 3: set the cutting depth to 2 mm." Which machine? Which material? Neither word is in the chunk, so a search cannot tell it from the same step in another manual.
  • Contextual retrieval: before indexing, add a short explanation of where the chunk comes from to the front of each chunk, then build the embedding search and the BM25 keyword search on those longer chunks. A model writes each prefix. Anthropic reports that this cut the top-20 retrieval failure rate by 35% with the embedding search alone (5.7% down to 3.7%), and by 49% when the keyword search used it too (down to 2.9%) (Contextual Retrieval). These are relative reductions in how often the right chunk was missing from the 20 retrieved, measured on Anthropic's own test sets, not on machine manuals, so treat them as a hint, not a promise.
  • It does not fix everything: a big window still costs on every step and still rots (Sections 2 and 3).

Worked example: the assistant 3 min

The gist: for every piece of information, ask one question: does this call need it now (keep), does a later session need it (save), or can it be fetched when asked (retrieve)?

Worked example

A student writes: "Can I use the 3D printer? What temp for PETG?"

  1. Keep in the window: the system prompt, the tool definitions and this chat. The model needs them on every step of this request, so they must be in each call (Section 1).
  2. Save between sessions: the student's training status ("3D printer trained, as of 3 October") and a booking preference ("afternoons") in students.json. A new session starts empty (Section 4), so the program loads this record at the start. The assistant can then answer "Can I use it?" without asking again.
  3. Retrieve from the manual: only the PETG chunk (and any safety chunk the search returns). Nobody pastes the whole manual, because it would be re-sent and billed each step (Section 5).
  4. Leave out: the laser cutter manual and other students' records. They add cost and distraction.

System prompt, tool definitionsKeepNeeded by every call
This chat and tool resultsKeep (clear old results)The thread of this request
Training status, preferencesSave, then loadNeeded next session
PETG chunkRetrieveNeeded once, small, found by search
Whole 3D printer manualDo not loadLarge, mostly irrelevant

Cost, with made-up numbers. Assume a 4-step request, an input price of $3 per million tokens (invented), no caching, and a 40,000-token manual (a model with a bigger window than Figure 1's toy limit). To keep it simple, ignore the history growth from Section 2; it adds to both cases.

  • With retrieval: about 1,560 tokens per call (300 system prompt, 700 tools, 200 chat, 60 saved record, 300 chunks). Over 4 calls: 6,240 tokens, about $0.02.
  • With the whole manual pasted instead of the chunks: 41,260 per call. Over 4 calls: 165,040 tokens, about $0.50.
  • That is more than 25 times the cost, and likely a worse answer because of context rot (Section 3). Both figures are illustrative, so use your real prices, and check what caching does to them, when you plan the budget.

Summary 2 min

  • The context window is everything the model sees in one call, including its own reply. It has a limit and you pay per token.
  • The model keeps nothing between calls. Each step re-sends the history, so cost is the sum of all calls; clear old tool results and compact when needed.
  • Between sessions only what your program saves (notes in a file or database) and loads back exists.
  • For long manuals, split into chunks, search, and put only the top few in the window. Retrieval can miss, and chunks lose context unless you add it.
