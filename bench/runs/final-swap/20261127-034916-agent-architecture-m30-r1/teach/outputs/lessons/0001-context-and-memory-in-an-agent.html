Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what stays in its context window, what it saves between sessions, and how it finds the right page in a long manual.

Warm-up 2 min

The gist. The agent loop is the frame for everything below. Context and memory decide what the model sees each time the loop turns.

The assistant you are designing answers questions such as "Is the laser cutter free on Friday?" It cannot know the answer from training, so it must act. The recall question below uses that request.

Recall

For "Is the laser cutter free on Friday?", name the four steps of the agent loop in order. Then say which part runs the calendar tool: the model, or the program around it.

Check your answer

First, the model asks for an action by writing a tool call, a written request that names a tool and its inputs, here a calendar lookup for Friday. Second, the program carries the action out. Third, the result returns to the model as text. Fourth, the loop repeats until the model has enough to answer.

The program runs the tool. The model only writes text. The program reads that request, runs the code and sends the output back. The same split holds throughout this lesson: when the assistant saves a note or fetches a manual page, the program does the work at the model's request. Today's question is what the model sees each time the loop turns.

1. The context window 4 min

The gist. Each step of the loop is a separate request to the model, and the model keeps nothing between requests. The program must send everything it needs every time, so cost grows with the size of what is sent.

A language model reads and writes in tokens. A token is a chunk of text, usually a short word or part of a longer one. The exact count for a page depends on the model, so every token number in this lesson is hypothetical and chosen for illustration.

A model call is one request in which the program sends text to the model and receives text back. The context window is all the tokens the model can see during one call: the instructions, the conversation so far, any tool results and the reply being written. The window is finite, and Anthropic's engineers describe context as a finite resource that must be used with care (Effective context engineering for AI agents).

One consequence follows from the loop you recalled. Every pass through the loop is a new model call. The model holds no state from the previous call, so the program resends the earlier text each time. This matches your earlier lesson on what a model does: it knows only its training and the text it is given, and that text is the window.

A session is one continuous conversation with one student, from the first message until it ends.

Cost follows from this. Providers typically charge by the tokens processed (some discount repeated text, so check your provider's pricing; this lesson states no prices). If a tool returns a 6,000-token manual page at call 2, that page is processed again at call 3, and again at every later call in the session.

Example: the cook and the order ticket

Imagine a cook who forgets everything after each plate. To keep the kitchen working, the server hands over the full order ticket, every item so far, before each plate. The ticket is the context window. The cook is the model. The server who writes and carries the ticket is the program.

The analogy fails in one place. A real cook skims a ticket and remembers the kitchen. The model rereads every token of the ticket on every call, and each reread is typically billed. A longer ticket makes every later plate more expensive.

Predict

A student asks one question. Call 1 makes the model request a manual page. Call 2 receives the page and requests the calendar. Call 3 writes the answer. Which calls contain the manual page?

Show the answer

Calls 2 and 3. The page is created after call 1 and then resent in full with the history. The "call 2 only" answer misses the resend; "all three" ignores that call 1 comes first; "none" assumes the model remembers, which it does not.

2. What is kept between steps 4 min

The gist. Within a session, the program keeps a growing list of messages and resends all of it at each call. Long tool results stay in that list, and a longer window does not mean a better one, so aim for the smallest useful set.

The program keeps the history as a list of messages. In Python it is a list of dicts, shown here in simplified form (real formats differ):

messages = [
    {"role": "system", "content": "You answer questions about makerspace machines."},
    {"role": "user", "content": "How do I change the laser cutter focus, and is it free Friday?"},
]
# Call 1 sends `messages`; the model asks for a manual page.
messages.append({"role": "assistant", "content": "tool call: get_page('laser-focus')"})
messages.append({"role": "tool", "content": "<the whole manual page, 6,000 tokens>"})
# Call 2 sends the entire list again, page included.

The role field says who wrote each message: system for the standing instructions, user for the student, assistant for the model, tool for a tool's output.

Each append adds the model's request or the tool's result, and the next call sends the full list. Nothing is removed unless the program removes it. The manual page therefore stays in every later call, even after the model has used it.

This matters beyond cost. Anthropic's engineers report that as the number of tokens in the window grows, the model's ability to recall specific information from it decreases. They call this context rot, and describe the model as having an "attention budget" that each extra token draws on (Effective context engineering for AI agents). Their guidance is to find the smallest set of high-signal tokens, meaning the tokens that most help the model's next decision, that makes the wanted result likely.

A window large enough to hold every manual removes the length ceiling. It does not remove the per-token cost, and it does not guarantee the model uses each token equally well.

3. Managing a full window 3 min

The gist. When history grows, the program can clear old tool results or summarise the conversation and restart from the summary. Both save tokens, and both can lose detail.

Two techniques address a growing list. Context editing automatically clears stale tool results, such as a manual page already used, from the window as it nears its limit while the conversation itself stays (Managing context on the Claude Developer Platform). The engineering article calls the same idea tool result clearing and describes it as one of the safest, lightest-touch forms of compaction.

Compaction in the fuller sense is a summary: when the conversation nears the window limit, the model is asked to summarise it, and a new window starts with that summary plus a little recent material (Effective context engineering for AI agents). It frees more space than clearing one result, but it loses detail.

Which technique to use depends on what fills the window. In the makerspace assistant, most tokens will come from tool results, mainly manual pages, so clearing old results is the first and cheapest step. Summarising is the later step, for a long conversation that still has to continue. Either can be set up to trigger automatically near the limit, or done by your own program, which edits the list before the next call; for a summary, the model writes the text.

The trade-off is detail. A summary keeps what the summariser judged important at that moment. A constraint that seemed minor, such as "I can only come on Fridays", may vanish and matter later. Clearing a manual page is low risk because the page can be fetched again; summarising a conversation is not reversible.

Example: the pass and the shift summary

A manager clears old receipts from the order pass but keeps the open order in view: that is context editing. At the end of a shift the manager writes a one-page handover for the next team: that is compaction. The analogy stops at authorship: the model writes its own summary, and unless the team adds a check, no one reviews it.

Sort

Place each item as keep, clear or summarise: (a) a 6,000-token manual page the model already used to answer; (b) the student's statement, "I only have Fridays free"; (c) forty turns of chat comparing which machines might suit a project, now settled.

Check your answer

(a) Clear: the page can be fetched again, and its tokens are stale. (b) Keep: it is short, high-signal and not recoverable once lost. (c) Summarise: the outcome matters and the forty turns do not. A common slip is to summarise (a), which spends effort on text that is recoverable, or to clear (b), which silently drops a requirement. Review: the trade-off paragraph above.

4. Between sessions: notes 4 min

The gist. When a session ends, the window is gone. To remember a student's training status next week, the assistant must write a note outside the window and read it back later, through tool calls the program runs.

When a session ends, the program discards the message list, and the next session starts with an empty window. Nothing in the model changes. So the context window is not memory in the sense you need for training status.

In this lesson memory means information saved outside the window, in a file or database, that is written in one session and read into the window in a later one. Anthropic describes structured note-taking as the agent regularly writing notes that persist outside the context window and are pulled back in later (Effective context engineering for AI agents).

The memory tool is Anthropic's tool for this: it lets the model store and retrieve information through a file-based system outside the window. It is client-side, meaning your own program executes the file operations and decides where files are kept (Managing context on the Claude Developer Platform). Writing a note is therefore a tool call like any other, as in Figure 2.

Two details prevent a common error. Nothing saves automatically: the model must call the memory tool, and the program's instructions must tell it when to write and when to read. Also, a note costs tokens when it is read back, so notes should stay short.

Anthropic reports one internal result on this. In its own internal evaluation, on an internal set of agentic search tasks, using the memory tool together with context editing improved performance by 39% over a baseline, and context editing alone by 29%; the post does not define the baseline or the performance measure. In a 100-turn web search evaluation, context editing let agents finish workflows that would otherwise fail from running out of context, and reduced token use by 84% (Managing context on the Claude Developer Platform). These are one company's measurements on its own tasks, not a guarantee for the makerspace assistant.

Example: the manager's notepad

A manager keeps a notepad by the pass: "Table 4 allergic to nuts." Next shift, the manager reads it before taking orders. The assistant's equivalent: "Student 4471: completed laser cutter safety; not 3D printer." The analogy fails because the manager remembers faces and knows to glance at the pad. The model has no such habit; it reads the note only if it is told to and calls the tool.

Write

A student writes, "I finished the laser cutter safety course today." In one line, write the note the assistant should save. Then state when the assistant reads it.

Check your answer

A good note is short and factual, for example: "Student 4471: laser cutter safety completed (as reported by student, 2026-11-26); 3D printer not completed." It is read at the start of any later session, before the assistant answers a booking question, by a memory-tool call that the program runs. Common faults: saving the whole chat, which wastes tokens; assuming the save happens automatically; or reading only when the student asks. Review: the two details paragraph above.

5. Retrieval: finding the right page 4 min

The gist. A long manual should not sit in the window all session. Keep a light index of names, and load one page on demand through a tool the program runs.

Suppose the assistant must answer from the manuals for every makerspace machine. The direct approach puts all of it in the window. Every call then processes every page, and the model must find the relevant lines among irrelevant ones, which is the problem of Section 2.

The alternative is just-in-time retrieval. The window holds lightweight identifiers, such as file names, page titles or links, and the model uses a tool to load the full content only when needed (Effective context engineering for AI agents). The model reads the index, decides that "laser-cutter-focus" is relevant and requests that page. As with notes, the program runs the tool. The model does not search the files itself.

A hybrid strategy preloads a small core that is always useful, such as opening hours and the list of machines, and leaves the rest on demand. The engineering article describes this as a practical middle course. Retrieval has costs: each fetch is another call, and runtime exploration is slower than having data ready. Its benefit is that only the relevant page costs tokens, and only from the call where it arrives.

Example: the recipe binder

A kitchen keeps a binder of two hundred recipes with an index. A cook who gets an order for risotto looks up the index and opens one recipe. The alternative is reading every recipe aloud before each order. The analogy breaks in one place: the cook sees the index at a glance, while the model sees it as tokens and picks only by the names and descriptions it is given. Clear identifiers therefore matter; the lesson on tool descriptions will return to this.

Decide: preload or fetch?

The team is deciding what the assistant has in its window when a session opens. Which set of three items is the best preloaded core?

6. Misconceptions and where it breaks 3 min

The gist. Five wrong ideas are tempting because a chat feels continuous. The design also fails in two cases: when the job is too small to need these tools, and when notes go stale.

Five common mix-ups
  1. "The model remembers earlier chats." Tempting because a chat feels continuous. In fact the program resends the history (Section 1) or reads a note back (Section 4); the model keeps nothing.
  2. "A bigger window means no management." Tempting because the length limit disappears. Per-token cost and context rot remain (Section 2).
  3. "Memory is the window." Tempting because the window is what the model "knows" mid-conversation. It ends with the session; memory is saved outside it (Section 4).
  4. "The model searches the manuals by itself." Tempting because the answer seems to appear from nowhere. The model only asks; the program runs the search or the fetch (Section 5).
  5. "Notes save automatically." Tempting because chat products appear to remember. Here the model must call the memory tool, and the program must tell it when (Section 4).

Two limits apply to the design. First, a short task or a tiny manual fits the window. If the whole set is two pages, an index and fetch step adds a call and a tool to build, and a note file adds reads and writes, for little benefit. Use the simplest design that fits.

Second, notes can be wrong. Suppose the note says "3D printer not completed" and the student completes the course the next day. Unless something updates the note, the assistant will refuse a booking the student is now entitled to. Each note needs a date, and the team needs a rule for who updates it, ideally by checking wherever the makerspace officially records training.

Spot the error

One sentence is wrong: "At the end of a session the assistant keeps its window, so next week it still knows which courses a student finished." Say what is wrong and what should replace it.

Check your answer

The window is discarded at session end. Next week the assistant knows the student's courses only if it saved a note and reads it back. Fix: save a dated note with the memory tool, and read it at the next session's start.

7. Worked example and practice 4 min

The gist. For one request, decide what is in the window, what is fetched and what is saved. Work through the laser cutter case, then try the 3D printer case.

Worked example

A returning student asks: "Can I book the laser cutter on Friday, and how do I change the focus?" The design decisions follow.

  1. Preloaded window. The program starts the session with the instructions, the opening hours, the machine list and an index of manual page names. These are small, used in nearly every session, and they let the model name a page. Reading the student's note is the model's first tool call, run by the program, because notes are not loaded unless asked for.
  2. Note read. The note says "laser cutter safety completed; 3D printer not completed." The model learns the student may use the laser cutter. This costs a few tokens.
  3. Fetch. The index shows a "laser-cutter-focus" page. The model requests it, the program runs the fetch and the 6,000-token page enters the window. The model also checks the Friday calendar through the booking tool.
  4. Cost check (illustrative; the small items are ignored). Count the calls: call 1 asks for the note, call 2 receives it and asks for the page and the calendar, call 3 receives both and writes the answer. Preloading all manuals would put 60,000 tokens in each of three calls: 180,000 in total. The index approach carries the 500-token index in each call, and the 6,000-token page arrives at call 3 only: 3 x 500 + 6,000 = 7,500 tokens. Had a fourth call been needed, the page would be resent once more.
  5. Answer and book. With the note, the page and the calendar result in the window, the model answers and books. Once the page has been used, the program may clear it (Section 3), since it can be fetched again.
  6. Save. The booking is recorded by the booking tool, not as a note. The model saves a note only if something new and durable was learned about the student, such as a completed course. This session produced none, so nothing is saved.

8. Summary and explain-back 2 min

  • The context window is everything the model sees on one call. Each loop step is a new call, so the program resends the history and cost grows with its size.
  • Context rot means more tokens can mean weaker recall, so keep the smallest set of high-signal tokens. Clearing stale tool results and compaction trim the window, and both can lose detail.
  • Memory is notes written outside the window through the memory tool, which the program runs. Nothing saves unless the model calls it.
  • Retrieval keeps identifiers in the window and loads a page on demand through a tool the program runs. Preload only the small core.

Say it in your own words: explain to a teammate why a bigger window does not replace notes and retrieval.

A model answer to the explain-back prompt

A bigger window only raises the limit on one call's text. The model still keeps nothing after the session ends, so a training status needs a saved note. Every extra token is still processed, and likely to be billed, on every call, and a crowded window can weaken recall, so a long manual is better fetched one page at a time.

Scope: this lesson covers retrieval as fetching a named page from an index. Searching by keyword or meaning is a further step. Other providers offer equivalents of the memory tool and context editing; the ideas, not the product names, are what to carry into your design.
