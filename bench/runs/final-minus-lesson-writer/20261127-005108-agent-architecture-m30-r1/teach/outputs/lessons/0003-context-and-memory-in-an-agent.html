Context and memory in an agent

By the end of this lesson you can sort the makerspace assistant's information into context, retrieval or saved notes, and say why each choice keeps cost down.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three come down to one question: what goes in front of the model at each step, and what stays outside until needed. That is the design decision you will defend at your review.

Warm-up 2 min

Last time you traced "Is the laser cutter free on Friday?" through the agent loop. Quick recall before we build on it.

Recall

Name the steps of the agent loop in order. After a tool runs, what goes back to the model?

Check your answer
  • The model asks for an action (a tool call), the action is carried out, the result goes back to the model, and this repeats until the model gives a final answer or a limit is reached.
  • What goes back is the tool's result, as text. Today's question: what exactly does the model see when that result arrives, and what happens to it afterwards?

Section 1: The context window 3 min

The model reads one block of text per call and writes a reply. It carries nothing over by itself. Whatever is in that block is all it knows right then.

  • Token: a chunk of text, roughly a word or part of a word, that the model reads and writes. Providers bill by tokens, so tokens are your cost unit.
  • Context: all the text sent to the model in one call: the system prompt (standing instructions you write), the tool definitions (descriptions of the tools it may call), the conversation so far, and any tool results.
  • Context window: the maximum number of tokens the model can handle in one call, input and output together (Claude docs: context windows). It limits how much fits, and every token inside it costs money.
  • Stateless: remembering nothing between calls. The model is stateless, so each call is a fresh start, and anything it should know must be sent again.

Example

  • Soccer: picture a referee who is handed the match report at every whistle and keeps nothing in their head. If the yellow card from minute 20 is not on the report, it did not happen. The context is that report.
  • Python: the model behaves like a pure function. reply = model(context) returns text and changes nothing. Call it twice with the same context and you start from the same place both times (the wording of the reply can differ, but nothing from the first call is remembered).
  • Where the analogy stops: a referee's report is short and written by people. The model's context also holds your instructions and tool descriptions, and it is far longer.
Check yourself

Show the answer

The third option. The model is stateless, so everything it needs on step 3 (instructions, tool definitions, the earlier steps) is sent again in that call.

Section 2: What is kept between steps 3 min

Your program keeps the history, not the model. Each loop it adds the new result to a list and sends the whole list again. So every step costs more than the last.

  • Message list: the list your program holds of everything said and done so far: the user's question, each tool call, each result. It is the conversation history that is re-sent each call.
  • The program, not the model, runs each tool, and each step is a separate model call. The loop is just your code appending to the list and calling the model again.

A sketch in Python-style pseudocode (the names are made up, not a real library's API):

messages = [{"role": "user", "content": "Is the laser cutter free Friday?"}]
while True:
    reply = call_model(system_prompt, tools, messages)   # sends EVERYTHING
    messages.append(reply)                               # keep the model's turn
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_call)                   # your code runs the tool
    messages.append(result)                              # keep the result for next time
  • call_model(system_prompt, tools, messages): the full context goes in on every pass. This is the line that costs money.
  • messages.append(...): the only "memory" between steps. Delete these lines and the model starts blind every loop.
  • run_tool(...): your code acts, not the model. The model only asks.

Example: the cost of one request

Token counts below are made up for illustration.

StepSent to the modelTokens sent
1Instructions + tools (1,500) + question (100)1,600
2Step 1 + the tool call (50) + calendar result (300)1,950
3Step 2 + the next call (50) + machine-rules result (400)2,400
  • Total input across the three calls: 1,600 + 1,950 + 2,400 = 5,950 tokens, though the new information is only 900 tokens (the question, two calls and two results).
  • The instructions and tools are paid for three times. The growth is not a bug; it is how a stateless model works.
  • These sums are the plain case: input tokens only, no discounts. Output tokens are billed too, and providers offer prompt caching (reusing an unchanged start of the prompt at a lower price), which changes what you pay for re-sent tokens but not whether they count toward the window (Claude docs: context windows). Check your provider's pricing page for the real rates.

Section 3: Keeping a growing context small 3 min

A bigger window does not mean you should fill it. Anthropic's guidance is to keep the smallest set of high-signal tokens (text that actually helps the next step) that gets the job done. Cut, compress, or clear what no longer helps.

  • Why: every token costs money, and models have a limited attention budget (only so much text can be weighed well at once), so more text can mean less focus on the part that matters (Anthropic: effective context engineering).
  • Compaction: summarizing a long history into a short version and continuing with the summary in place of the full history.
  • Three moves for what is already in context:
    • Keep: what the next step needs, such as the instructions and the student's current request.
    • Summarize: a long exchange whose outcome matters but whose wording does not.
    • Clear: an old tool result you have already used, such as a calendar listing from ten steps ago.

Example

  • NFL: a coach goes into the game with a play card, not last season's whole binder. Keep the game plan, drop last week's notes.
  • The assistant: if it pastes a 40-page laser cutter manual into context at step 1, those pages are re-sent and billed on every later step, though the question needed one paragraph.
  • Where the analogy stops: a coach chooses the card once. Your program must decide this at every loop.

  2. A 600-token calendar listing from step 4. Its one relevant fact (Friday 2 pm is taken) is already in the booking decision.
  3. Fifteen back-and-forth messages in which the student and assistant settled on a laser cutter, 3 mm acrylic, and a Friday slot.

Show the answer
  1. Keep. Needed on every call.
  2. Clear. The fact was used; the tool can be called again if it is ever needed. Wrong? Review section 2: re-sent tokens cost on every later step.
  3. Summarize. The outcome matters (machine, material, slot), the wording does not. Keep exact values such as the time in the summary.

  5. Clear. Used already and re-fetchable, like item 2.

Common slip: summarizing item 2 or 5. That is extra work for something you can simply drop, and a summary risks losing a detail (section 8).

Section 4: What is kept between sessions 2 min

By default, nothing. When a session ends, the message list is gone. A new session starts with an empty context. Anything that must last has to be stored outside the model and loaded back in.

  • Session: one run of the assistant from first message to end, with its own message list.
  • The model's knowledge from training does not change when it talks to you. Chatting with it does not teach it.
  • So "memory" across sessions is something you build: write information to a place you control (a file, a database), then read it into the next session's context.

Example

  • A student finishes laser training on Monday. On Thursday they open a new session and the assistant asks whether they have been trained. Nothing was saved, so nothing was there to load.
  • NBA: a new season starts and the coach has the same players, but the roster sheet must be handed over again, or nobody knows who has what skills.

Section 5: Retrieval 3 min

Instead of loading the whole manual, give the assistant a search tool. It finds the few relevant passages and only those enter the context.

  • Retrieval: fetching just the pieces of stored information that a question needs, at the moment it needs them. Anthropic describes a related "just in time" approach, where an agent keeps lightweight pointers such as file paths and loads data through tools only when needed, instead of loading everything up front (Anthropic: effective context engineering). Chunk-and-search retrieval, below, is one common way to do this for a long manual.
  • Chunk: a small piece of a document, such as one section of a manual, that is stored and searched on its own.
  • Keyword search: finds chunks that contain the exact words of the query.
  • Embedding: a list of numbers that places a piece of text so that texts with similar meaning land close together. Searching by closeness finds chunks that mean the same thing even with different words. You do not need the math today.

Example

  • Question: "What speed should I use for 3 mm acrylic?" The search tool returns the two best chunks from the laser cutter manual. Maybe 1,000 tokens (two chunks of about 500, an illustrative figure) enter the context instead of 40 pages.
  • Data science: this is a query against an index instead of a full table scan. You pay to build the index once, then each lookup is cheap.
  • Keyword search suits an exact term like "kerf". Similarity search suits "why is my cut burning", where the manual may say "scorching" or "excess heat".
Check yourself

Two queries come in. Query A: "what is the kerf setting?" (kerf is the manual's exact term). Query B: "my cut keeps coming out scorched, what do I change?" (the manual says "excess heat" and "charring"). Which pairing of search types fits best?

Show the answer

Keyword for A, similarity for B. Similarity search matches meaning, so different wording still finds the chunk; keyword search is precise for an exact term such as a part number.

Section 6: Notes as memory 3 min

Give the assistant a tool to write notes to a file and read them back. The file survives the session, so next time the assistant loads what it saved.

  • Memory tool: a tool that lets the model store and retrieve information across conversations in a directory of memory files. In Anthropic's version it runs on the client side: the model only requests an operation and your application carries it out against storage you control (Claude docs: memory tool).
  • This is the same pattern as any tool: the model asks, your code acts. Your code decides where the files live and who may read them.
  • Notes are small, written on purpose, and read back at the start of a session. Anthropic describes this as structured note-taking, with the agent writing notes outside the context window to pull back in later.
  • Cost (illustrative): a notes file of a few lines is perhaps a hundred tokens to read, against thousands to re-send a whole old chat. Memory by notes is cheap because it is small and chosen, not a transcript.

Example

# students/riley.md
- laser cutter: trained 2026-10-12, certified until 2027-10-12
- 3D printer: not trained
- prefers booking Friday afternoons
  • Session 1: after training, the model asks the memory tool to save the lines above.
  • Session 2: the first step reads students/riley.md, and the assistant can say, "You are certified on the laser cutter. Want a Friday afternoon slot?"
  • Sports: a scouting report. It is written once, short, and handed over before the next game.
  • Where the analogy stops: a scouting report is written by a person after the fact. Here the model chooses what to write, so you need to check what it saves.
Your turn

Write the note the assistant should save after a student finishes 3D printer training. Then say when it should read that note.

Show a model answer
  • Note: the student's identifier, "3D printer: trained", the date, and when it expires if training lapses. A few lines, not the chat.
  • Read: at the start of the next session, or before a booking, so the answer to "can they use this machine?" comes from the file and not the model's guess.

Section 7: Common mix-ups 2 min

Mix-up 1: the model remembers on its own

Tempting because a chatbot app seems to remember you. That app is storing and re-sending your history for you. The bare model is stateless (section 1), so your design must do it.

Mix-up 2: a bigger window means no management

Tempting because more room sounds like fewer problems. But every token is billed on every step (section 2), and extra text can dilute focus (section 3).

Mix-up 3: everything in the window is used equally well

Tempting because "it can see it all". But as the token count grows, accuracy and recall can degrade (the docs call this context rot), so a relevant paragraph buried in 40 pages can be at more risk than the same paragraph alone (Claude docs: context windows).

Mix-up 4: memory means the model learning

Tempting because we say it "remembers". Saved notes are files read back into context. The model's weights, the numbers it learned in training, never change.

Mix-up 5: retrieval and memory are the same

Tempting because both load stored text. Retrieval looks up existing material you prepared, such as the manuals. Memory is what the agent writes for itself, such as a student's status. They can share storage, but the question differs: "what is true in the manual?" versus "what happened before?"

Spot the wrong claim

Which team-chat message is wrong?

Show the answer

The second message. Saved notes are text in a file; the model only benefits when your code loads them into its context.

Section 8: Where this breaks 2 min

Each tool here can fail quietly. Know the failure for each so you can design a check.

  • Retrieval returns the wrong chunk. A question about the 3D printer pulls up the laser cutter's page because both mention "bed temperature". Fix: tag chunks with the machine name and filter by it, and tell the model to say so when the results do not answer the question.
  • Compaction drops a detail. A summary says "booked Friday" and loses the time. Fix: keep exact values such as times and IDs outside the summarized text.
  • Notes go stale. The file says "trained on laser", but the certification expired. Fix: store expiry dates with each note and check them before acting.
  • Too much in context. The model gets distracted by irrelevant text. Fix: load less (section 3).
Predict the failure

The notes say "Sam: laser trained 2025-03-01, valid one year". It is now December 2026 and the assistant books Sam on the laser cutter. What went wrong, and what is one fix?

Show the answer

The note is stale: the assistant trusted it without checking the date. One fix is to have the code compare the expiry date to today's date before booking, and not rely on the model to notice.

Worked example and practice 5 min

Three places hold information: the context (sent every step), retrieval (fetched when needed), and notes (saved between sessions). Pick by how often the model needs it and how long it must last.

Worked example

Sort six pieces of makerspace-assistant information.

  2. Ask: is it big but only partly needed? Then retrieval.
  3. Ask: must it survive the session? Then notes.
  4. Cost line (illustrative numbers): say 40 pages is about 25,000 tokens. In context for a 6-step request that is 6 × 25,000 = 150,000 input tokens. A saving of roughly 146,000 tokens on one request, before counting the instructions.

Summary 2 min

  • The model is stateless: each call sees only the context sent to it, and every token costs money.
  • Between steps, your program keeps the message list and re-sends it, so cost grows each loop. Keep, summarize or clear.
  • Between sessions nothing survives unless you store it: notes as files, written and read through a tool your code runs.
  • Retrieval fetches just the needed chunks from material you prepared, so the manual stays out of context.
